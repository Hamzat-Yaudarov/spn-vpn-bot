# Переход Way SPN с Remnawave 2.8.1 на 3.4.1

Подготовлено 31.08.2026. Это порядок действий, а не отчёт о выполненном обновлении сервера.
Команды выполняются по разделам, с проверкой результата после каждого. При ошибке не продолжайте.

## Где выполнять команды

- **Сервер панели**: каталог `/opt/remnawave`; здесь панель, её PostgreSQL, nginx и страница подписок.
- **Сервер бота**: каталог `/root/spn-vpn-bot`; здесь бот, MiniApp и сайт. Его база — отдельная Supabase.
- **Серверы нод**: на первом этапе не трогаем.

Бот упоминается только из-за совместимости: в API 3 вместо старого UUID используется числовой ID.
Миграция панели удаляет старое поле UUID. Поэтому соответствия сохраняем **перед** переходом.
Ключи подключения, ссылки подписок, сроки, оплаченный трафик и локальные UUID скрипт подготовки не меняет.
Основание: [изменения Remnawave 3](https://github.com/remnawave/backend/releases/tag/3.0.0).

## 1. Сервер панели: первая резервная копия без остановки

Скопируйте блок целиком. Он создаёт новый закрытый каталог, не перезаписывая старые копии.

```bash
(
  set -eu
  umask 077
  backup_dir=$(mktemp -d /root/rw-before-v3-XXXXXXXX)
  docker exec remnawave-db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup_dir/remnawave.dump"
  test -s "$backup_dir/remnawave.dump"
  docker exec -i remnawave-db pg_restore --list < "$backup_dir/remnawave.dump" > /dev/null
  tar -czf "$backup_dir/configs.tar.gz" -C /opt remnawave
  tar -tzf "$backup_dir/configs.tar.gz" > /dev/null
  docker inspect --format '{{.Name}} {{.Config.Image}} {{.Image}}' remnawave remnawave-db remnawave-redis remnawave-subscription-page > "$backup_dir/images.txt"
  ls -lh "$backup_dir"
)
```

Сохраните показанный путь. `pg_restore --list` проверяет чтение оглавления дампа, но не заменяет тестовое восстановление. Архив содержит секреты: скачайте его себе для хранения, но не присылайте в чат и не загружайте в GitHub.

Теперь проверьте состав установки:

```bash
cd /opt/remnawave
docker compose config --images
docker compose ps
df -h / /var/lib/docker
```

Ожидается backend 2.x и существующие БД/Redis. Если установка отличается, сначала уточните конфигурацию.
Сохраните текущие образы до завершения проверки; не делайте `docker image prune`.

## 2. Сервер бота: поставить подготовленный код, оставаясь на API 2

Сначала сохраните актуальную резервную копию базы бота средствами Supabase и локальную копию `.env`.
Изменённый код нужно доставить в `/root/spn-vpn-bot` обычным способом. Если используете GitHub,
сначала опубликуйте изменения проекта, затем выполняйте `git pull --ff-only origin main`.
Сам по себе `git pull` не скачает неопубликованные локальные изменения. Не заменяйте серверный `.env` примером.

Нужны обновлённые `config.py`, `database.py`, `services/remnawave.py`, новые
`services/remnawave_identity.py` и `scripts/prepare_remnawave_v3.py`.

В `.env` **бота** пока оставить или добавить:

```dotenv
REMNAWAVE_API_VERSION=2
```

Сначала проверка, без изменения базы:

```bash
cd /root/spn-vpn-bot
./venv/bin/python scripts/prepare_remnawave_v3.py
```

Нужно увидеть `Нет соответствия среди действующих подписок: 0`.
Если число больше нуля или есть ошибка — панель пока не обновлять. Секреты скрипт не печатает.
Отсутствующие старые неактивные профили считаются отдельно: они не удаляются и не пересоздаются.

Затем сохранить карту ID в базе бота и отдельном файле:

```bash
./venv/bin/python scripts/prepare_remnawave_v3.py --apply --output "/root/remnawave-id-map-$(date +%Y%m%d-%H%M%S).json"
sudo systemctl restart spn-bot
sudo journalctl -u spn-bot --since "2 minutes ago" --no-pager -n 80
```

Карта — не полный бэкап панели. Скрипт изменяет только новую таблицу `remnawave_user_identities` в базе бота;
обычные миграции всего проекта через него не запускаются. Повторный запуск безопасен для совпадающих записей;
противоречие останавливает операцию, а файл с прежним именем не перезаписывается.

Проверьте `/start`, список подписок и устройства при ещё работающей панели 2.8.1.
Код сохраняет ID и у новых пользователей API 2, созданных до следующего этапа.

## 3. Согласованное окно обновления

Дальше будет краткая недоступность покупки/управления. Не обещайте пользователям отсутствие перерывов.
Не создавайте новые платежи во время окна; после запуска сверьте оплаты, пришедшие в это время.
Не выполняйте ручные изменения пользователей в панели между финальной картой ID и обновлением.

На **сервере бота** остановить обработку и сохранить окончательную карту, пока панель ещё работает на API 2:

```bash
cd /root/spn-vpn-bot
sudo systemctl stop spn-bot
./venv/bin/python scripts/prepare_remnawave_v3.py --apply --output "/root/remnawave-id-map-final-$(date +%Y%m%d-%H%M%S).json"
```

Если проверка не прошла — оставьте панель на версии 2, запустите `sudo systemctl start spn-bot` и разберите ошибку.

На **сервере панели**:

```bash
cd /opt/remnawave
docker compose stop remnawave
```

Повторите блок резервного копирования из раздела 1: он создаст отдельный каталог для окончательного состояния.
БД не останавливайте, она нужна для дампа. Зафиксируйте путь **финальной** копии.
Перед изменением схемы желательно проверить восстановление дампа в отдельную БД/на отдельном тестовом сервере.
Если окончательная копия не получилась — не обновляйте образ, верните прежнюю панель и бот.

## 4. Сервер панели: изменить только нужное

В `/opt/remnawave/.env`:

- Если уже есть непустой `APP_SECRET`, оставьте его значение.
- Если есть только `JWT_AUTH_SECRET`, переименуйте **имя** переменной в `APP_SECRET`, сохранив значение полностью.
- Не генерируйте новый секрет. Не меняйте пароли БД, домены, API-токены и параметры Redis заодно.

Это требование [конфигурации 3.4.1](https://github.com/remnawave/backend/blob/3.4.1/src/common/config/app-config/config.schema.ts).

```bash
cd /opt/remnawave
nano .env
nano docker-compose.yml
```

В `docker-compose.yml` замените только строку образа сервиса `remnawave`:

```yaml
image: remnawave/backend:3.4.1
```

Используем конкретный [релиз 3.4.1](https://github.com/remnawave/backend/releases/tag/3.4.1), а не плавающий `latest`.
**Не заменяйте compose целиком**: в новом шаблоне другие PostgreSQL и точки монтирования.
Существующий PostgreSQL 17, его тома, Redis, сети, порты и nginx здесь остаются прежними.

Проверка и запуск только панели:

```bash
docker compose config --quiet
docker compose pull remnawave
docker compose up -d --no-deps remnawave
docker compose logs --tail=100 --no-color remnawave
docker compose ps
```

Выполняйте команды по очереди, только после успеха предыдущей.
Дождитесь завершения миграций и запуска приложения. Если контейнер перезапускается или в логах ошибка — остановитесь.
Не пытайтесь просто вернуть образ 2 поверх уже изменённой БД.

После успешного запуска обновить разрешение адреса контейнера в nginx:

```bash
docker exec remnawave-nginx nginx -t
docker exec remnawave-nginx nginx -s reload
curl -sS -o /dev/null -w 'Панель: HTTP %{http_code}\n' https://panel.wayspn.online/auth/login
```

Reload делать только при успешном `nginx -t`. Он нужен и после возможного пересоздания страницы подписок.
Откройте панель, войдите заново и проверьте версию, количество пользователей, профили, хосты и состояние нод.
HTTP 200 сам по себе не доказывает работоспособность API и всех функций панели.

## 5. Страница подписок и ноды

Не меняйте ссылки пользователей и домены. Сначала проверьте **существующую настоящую ссылку подписки**, а не корень sub-домена.
Проверьте и страницу в браузере, и обновление профиля в Happ/INCY.

На сервере панели:

```bash
cd /opt/remnawave/subscription
docker compose ps
docker compose logs --tail=60 --no-color
```

Если старая страница несовместима с API 3, её обновление — отдельный шаг после резервной копии её `.env`,
compose и сохранения старого образа. Не заменяйте конфиги новым шаблоном; в штатной установке для страницы
используется `remnawave/subscription-page:latest`. Перед обновлением загрузите образ и запишите его digest,
чтобы знать точную запущенную сборку. Сверьте этот шаг с [инструкцией страницы подписок](https://docs.rw/install/subscription-page/bundled/).

Ноды обновляются **после панели, по одной**, с проверкой подключения после каждой. Это порядок из
[официальной инструкции обновления](https://docs.rw/install/upgrading/). Массовое обновление всех нод
в этот набор команд не включено: сначала проверить их текущие версии и необходимость обновления.

## 6. Сервер бота: проверить API 3 и включить обработку

Пока бот остановлен:

```bash
cd /root/spn-vpn-bot
./venv/bin/python scripts/prepare_remnawave_v3.py --check-v3
```

Нужны успешная проверка и ноль отсутствующих соответствий действующих подписок.
HTTP 401/403 — проверить API-токен/его права; не вставлять вместо него пароль от панели.
При расхождении ID/имени не запускайте бота и не пересоздавайте пользователей автоматически.

Только после успешной проверки в `.env` **бота** изменить:

```dotenv
REMNAWAVE_API_VERSION=3
```

```bash
nano .env
sudo systemctl start spn-bot
sudo journalctl -u spn-bot --since "2 minutes ago" --no-pager -n 100
```

Проверить на своём тестовом аккаунте: старый ключ, список подписок, устройства, новую покупку и продление,
докупку ГБ/устройств, выдачу результата оплаты. Оплаченные ГБ и сроки не должны измениться сами по себе.
Удаление/деактивацию проверять только на отдельной ненужной тестовой подписке, не на клиентах.
На API 3 установка прошедшего срока отключает профиль через `DISABLED`; бот хранит точный локальный срок.
Обычное продление включает его обратно. Не нужно сбрасывать трафик всем пользователям ради перехода.

## Если что-то пошло не так

Сохраните последние логи, версию образа и путь финального бэкапа. Не запускайте очистку томов,
`docker compose down -v`, `docker system prune --volumes` или ручное удаление таблиц.

Откат **после миграции** требует восстановления полной БД панели из финального дампа вместе со старым
образом и `.env`. Безопаснее восстановить копию в отдельную БД/том PostgreSQL той же основной версии,
проверить её, затем переключить прежнюю панель на неё. Текущий том не удалять.
Копия только `docker-compose.yml` или карта ID эту задачу не решает.

Если после обновления уже принимались оплаты, простой откат старого дампа потеряет изменения после него —
сначала нужна сверка с базой бота. До первого запуска бота 3 такой риск существенно меньше.
При возврате панели на 2 вернуть `REMNAWAVE_API_VERSION=2` у бота. Новую таблицу соответствий удалять не требуется.

## Проверки кода

```bash
python3 -m unittest discover -s tests
```

Автотесты проверяют оба формата ID, сохранение UUID, отсутствие создания при ошибке поиска, лимиты,
HWID, отключение/продление, правильный endpoint сквада, приватный экспорт, пагинацию и конфликты карты ID.
Они используют имитацию API/БД и не заменяют проверку на тестовой копии реальной панели.
