# Проверка и замена IPv4 для Way SPN

Контроллер рассчитан на отдельный пилотный сервер или входной relay.
Python 3.11+. Для первого запуска нужен проверяющий узел с российским
исходящим подключением и контрольная проверка вне РФ. Контрольную проверку
можно запускать на самом контроллере, если он расположен вне РФ.
В примере настроены две российские сети. Каждый проверяющий узел запускает
Xray с одним тестовым выходом и проверяет HTTPS через него. Отдельный
рабочий выход с тем же транспортом помогает отличить сбой VPN-входа
от сбоя самой проверки.

Из корня репозитория:

```sh
python3 -m spn_ip_failover --config spn_ip_failover/config.example.json plan
```

Для пилота скопируй пример в приватный файл, укажи свой URL панели, SSH-алиасы,
UUID и адреса. Включи токен Remnawave через переменную окружения
`REMNAWAVE_API_TOKEN`. Для просмотра нужны `nodes:read` и `hosts:read`, для
применения также `nodes:update` и `hosts:update`. Для обычных A-записей Cloudflare
нужен `CLOUDFLARE_API_TOKEN` с доступом на редактирование нужной зоны.
Хост с адресом-именем описывается полем `name`, хост с адресом-IP — без него.
Для ноды аналогично можно задать `node_name`. Для стабильных имён меняется
A-запись, для буквального IP меняется адрес в Remnawave. Имена, используемые
для переключения, должны иметь одну управляемую A-запись, без альтернативной
AAAA или проксирования Cloudflare. Если DNS у другого оператора или адрес
используется как CDN origin, потребуется отдельная интеграция.

```sh
python3 -m spn_ip_failover --config /etc/spn/rotation.json inventory
python3 -m spn_ip_failover --config /etc/spn/rotation.json check
python3 -m spn_ip_failover --config /etc/spn/rotation.json status
```

`inventory` читает все ноды и хосты панели, чтобы заполнить UUID.
`check` проверяет входы из инвентаря и показывает состояние связи панели с
соответствующей нодой. Для постоянного мониторинга без покупок убери `provider`
и `dns` из описания сервера и задай `manage_visibility: false`. Поле
`manage_visibility` по умолчанию включено для сервера с адаптером хостинга.
В этом режиме хост исчезает из новых подписок только после исчерпания лимита,
очистки кандидатов и повторного подтверждения отказа. Если хост восстановится,
контроллер вернёт его в выдачу.
Ноды не отключаются: их статус показывается отдельно. Изменения относятся
только к UUID, внесённым в инвентарь. Изменение списка у клиента зависит от
обновления подписки.

### Проверяющие узлы

На каждый проверяющий узел скопируй пакет и существующий
`ops/host-health-audit/e2e.py`, сохранив структуру каталогов. Нужны Python,
`/usr/bin/curl` и Xray. Укажи абсолютный путь и SHA-256 своего бинарника Xray.
Проверь ключи SSH перед запуском и используй отдельные SSH-учётные записи для
проверок. Храни `routes.json` в каталоге владельца с режимом `0700`, сам файл
с режимом `0600`:

```json
{
  "xray": "/opt/xray/xray",
  "sha256": "sha256-проверенного-бинарника",
  "routes": {
    "vpn-pilot-grpc": {
      "probe": {},
      "control": {}
    }
  }
}
```

Вставь в `probe` и `control` по одному полному объекту Xray outbound из
тестовых конфигураций. Ключ совпадает с `hosts[].key` в инвентаре. `control`
должен использовать отдельный, доступный адрес с тем же протоколом,
транспортом и шифрованием. У `probe` должны совпадать порт и имя хоста с
Remnawave. Для TLS/REALITY задай стабильное имя сервера явно. Для замены IP
воркер меняет только адрес подключения, сохраняет настройки транспорта
и проверяет существующий тестовый HTTPS-маршрут до
`https://www.gstatic.com/generate_204`. Выбирай отдельные учётные данные
тестового VPN. Не сохраняй приватные конфиги или токены в Git.

### Покупка и переключение

Контроллер вызывает команды адаптера из поля `providers` и передаёт им
JSON на stdin. Для XorekCloud есть адаптер BILLmanager
`python3 -m spn_ip_failover.xorek`. Список адресов и удаление используют
операции BILLmanager для конкретной услуги. Платный заказ требует
проверенной формы из кабинета. Для 1Cent есть браузерный адаптер для услуг
с кнопкой «Заказать IPv4». Команды настройки сети зависят от конфигурации
гостевой ОС.

| Команда | Что получает и возвращает |
| --- | --- |
| `check` | `operation`, `server_id`. Подтверждает возможность работы с этим VPS, управление адресами и наличие лимита на оплату в аккаунте, если он задан. Ответ `{"ok":true}`. |
| `inventory` | `operation`, `server_id`. Возвращает все назначенные публичные IPv4 этого VPS, включая исходный: `{"allocations":[{"id":"allocation-id","ip":"ipv4"}]}`. Без этого списка контроллер не делает покупки. |
| `allocate` | Также `request_id`. Заказывает один IPv4 для данного VPS. Ответ `{"id":"allocation-id","ip":"ipv4"}`. Храни связь между `request_id` и заказом. |
| `prepare` | Также `id`, `ip`. Назначает адрес в хостинге и гостевой ОС, сохраняет конфигурацию после перезапуска и оставляет старый IP. Ответ `{"ok":true}`. |
| `activate` | Также объекты `old` и `new`, каждый с `id` и `ip`. Применяет постоянную настройку гостевой ОС. При вызове с обратным порядком возвращает исходную. Ответ `{"ok":true}`. |
| `release` | Также `id`, `ip`. Сверяет точное назначение, удаляет его из гостевой ОС и освобождает у хостера. Повтор после успешного удаления возвращает `{"ok":true}`. |
| `retire` | Необязательная операция удаления прежнего рабочего адреса. Получает `old` и `current` с `id` и `ip`. Используется в 1Cent для смены главного IPv4. Ответ `{"ok":true}`. Если команда отсутствует, контроллер вызывает `release`. |

`provider_gateway` перед `check` и каждым `allocate` сначала проверяет
принадлежность текущего адреса услуге и вызывает гостевой `check`. Для
`managed_guest` это проверка уже завершённого bootstrap, журнала, адресов,
исходящего маршрута и хеша постоянной сетевой конфигурации без изменений
файлов или сети. Незавершённая операция или расхождение блокируют покупку.
Включённые старые службы `spn-reality-source-*.service` также блокируют
передачу управления: при подключении VPS нужно отдельно подтвердить их
принадлежность установщику и отключить старую загрузочную настройку.
Одна лишь проверка баланса в хостинге готовность VPS не подтверждает.

Используй абсолютные пути к исполняемым файлам. Команды `prepare`,
`activate` и `release` должны безопасно повторяться после прерывания
процесса. Для совместимого Linux VPS существующий
[`ops/ip-move/ip_move.py`](../ops/ip-move/ip_move.py) можно вызвать на этапе
`activate`: он меняет исходящий маршрут после назначения адреса. Постоянное
изменение он поддерживает для конкретной схемы ifupdown. Модуль
`spn_ip_failover.guest` оборачивает эту операцию для команд `prepare` и
`activate`. Его запускают на нужном VPS через заранее проверенный SSH-алиас,
с установленной root-копией пакета и `ops/ip-move/ip_move.py`:

```sh
cd /opt/wayspn
/usr/bin/python3 -B -m spn_ip_failover.guest --server-id ID_УСЛУГИ --interface ИНТЕРФЕЙС
```

Помощник проверяет, что провайдер уже назначил новый адрес на правильном
интерфейсе. На VPS, где адрес не назначается автоматически или используется
другая сеть, настрой `prepare` и `activate` под конкретную конфигурацию.
Для отката оба адреса должны оставаться назначенными, в том числе после
перезапуска. Если хостинг не снимает IP с гостевой ОС при освобождении,
команда `release` должна также удалить этот адрес из гостевой конфигурации.

```sh
python3 -m spn_ip_failover --config /etc/spn/rotation.json --state /var/lib/spn-ip-failover run --apply --watch
```

Укажи отдельный приватный каталог журнала с режимом `0700`. Один процесс
применяет изменения, а `status` читает снимок журнала параллельно. После
нескольких отказов одного хоста из обеих сетей РФ при рабочем подключении
извне контроллер заказывает по одному IPv4 и сразу проверяет его. Новый IP
должен пройти проверку всех настроенных хостов этого VPS. Не прошедшие
проверку адреса остаются назначенными, чтобы следующий заказ не получил
тот же адрес из освобождённого пула. Предел `max_ips_per_server` включает
первичный и ранее назначенные IPv4. Когда все десять слотов заняты, контроллер
может освободить только свой ранее отклонённый кандидат: сначала сохраняется
точный снимок назначений, затем проверяется удаление. Это позволяет сделать
до десяти покупок при десяти одновременных IP, не удаляя текущий или чужой адрес.
Повторно выданный ранее отклонённый IP расходует попытку заказа, но не считается
новым кандидатом и не проходит повторную VPN-проверку.

Отдельный `max_attempts` ограничивает число запросов заказа для одного сервера
до следующего явного разрешения оператора. Каждая попытка записывается до
отправки; восстановление связи, новый цикл и перезапуск не обнуляют счётчик.
Возврат оплаты за удалённый адрес также не выдаёт новые попытки. Когда доверенный
адаптер явно подтверждает отказ бюджета **до отправки** заказа, покупка не
считается совершённой: неудачные кандидаты очищаются, повтор возможен не раньше
чем через час и только при свежем подтверждении отказа из РФ. Неоднозначный ответ
обычным отказом бюджета не считается и требует сверки заказа.

При исчерпании лимита контроллер освобождает купленные им нерабочие адреса
и скрывает подтверждённо нерабочие хосты. Когда кандидат проходит проверку,
контроллер обновляет сервер, Remnawave и DNS, повторяет проверку по
опубликованным адресам и освобождает отклонённые варианты. При отказе
после публикации он возвращает старые значения, пока оба IP назначены.
Период `retire_seconds` должен покрывать прежний TTL DNS. Исходный адрес
освобождается после этого периода только при `release_initial: true`,
если хостинг допускает удаление. Остальные заранее назначенные адреса
считаются в лимите, но контроллер их не удаляет. Проверь другие DNS-записи
и ссылки на IP за пределами описанного инвентаря.

Если покупка осталась без ответа, найди результат по `request_id` у хостера.
На время сверки останови процесс применения. Если адрес выделен, укажи
подтверждённые реквизиты назначения. Если хостер подтвердил отсутствие
покупки, используй `--no-purchase`. Уже потраченная попытка сохраняется.

```sh
python3 -m spn_ip_failover --config /etc/spn/rotation.json --state /var/lib/spn-ip-failover reconcile \
  --server vpn-pilot --request REQUEST_ID --allocation-id ASSIGNMENT_ID --ip PUBLIC_IPV4
```

После проверки причины отказа оператор может явно разрешить новую серию
одному серверу, без ручного редактирования журнала:

```sh
python3 -m spn_ip_failover --config /etc/spn/rotation.json --state /var/lib/spn-ip-failover reset-limit \
  --server vpn-pilot --apply
```

Команда не меняет текущий IP, адреса панели, историю кандидатов или денежный
бюджет. Незавершённые покупки и ожидающее освобождение адресов блокируют сброс;
сначала их нужно завершить или сверить. Для нового разрешения снова собираются
свежие серии проверок, а прежний счётчик сохраняется в истории сбросов.

Перед включением на рабочем сервере проверь один пилот, включая перезапуск
VPS, откат и освобождение тестового дополнительного IP. Remnawave и
Cloudflare читаются до и после изменения, но единой транзакции между
хостером, сервером, панелью и DNS нет. Для управляемых записей используй
одного контроллера и учитывай ручные правки во время переключения.

Для непрерывной работы после перезагрузки используй
[готовый systemd unit и инструкцию](deploy/README.md).

Для Xorek перед включением покупки запроси только метаданные формы после
обычного входа или с отдельно настроенными учётными данными BILLmanager:

```sh
printf '%s\n' '{"operation":"discover","server_id":"ID_УCЛУГИ"}' |
  python3 -m spn_ip_failover.xorek
```

`discover` читает только имена кнопок и функций панели. Он не отправляет
заказ. Токен сеанса и пароль передаются через отдельный приватный источник.
Используй `inventory` с тем же `server_id`, чтобы узнать точный ID исходного
назначения. После проверки формы заказа укажи её параметры в файле
`XOREK_BILLMANAGER_ORDER_CONFIG`:

- `function`, `button_name`, `server_parameter` и `fixed_fields` из
  подтверждённой формы для выбранного существующего VPS.
- `quantity_parameter` и `quote_quantity_field` для заказа ровно одного
  адреса. `single_address_only: true` используется только если у формы
  подтверждено отсутствие выбора количества.
- `quote_server_field`, `quote_price_field`, `quote_currency_field` для
  сверки VPS, цены и валюты перед запросом.
- `maximum_rub` как строка с пределом цены за один заказ и `journal_path`
  как абсолютный путь к отдельному приватному каталогу заказов.

Операция `quote` проверяет, что форма доступна и отдаёт цену в RUB для
указанного VPS, без отправки заказа. Для команд `check`, `inventory`,
`allocate` и `release` в контроллере можно задать argv
`["/usr/bin/python3","-B","-m","spn_ip_failover.xorek"]`. Сценарий покупки
поддерживает один подтверждённый запрос BILLmanager. Если поставщик
отправляет заказ в корзину, потребуется отдельно сверить процесс оплаты.
Результат запроса подтверждается появлением ровно одного нового IPv4.
Если ответ неоднозначен, повторный заказ по тому же запросу не отправляется.

При неоднозначном заказе Xorek сначала сверь операции в кабинете. Если в
журнале Xorek есть неподтверждённая запись, перед сверкой журнала контроллера
вызови `python3 -m spn_ip_failover.xorek` с операцией `reconcile`,
`server_id`, `request_id` и полем `allocation` со значением `null` или
`{"id":"ID_НАЗНАЧЕНИЯ","ip":"IPv4"}`. Адаптер сверит результат по списку
назначенных адресов. Для `null` нужно отдельно убедиться, что хостинг
отменил запрос и не спишет средства позднее.

### Кабинет 1Cent

На контроллере потребуется Python Playwright с Chromium. Скопируй
[`onecent.example.json`](onecent.example.json) в приватную конфигурацию и
укажи в `servers` точный UUID из адресной строки услуги, имя из заголовка
кабинета и пределы разового списания и ежемесячного продления за один IPv4.
У сервера в основном инвентаре `server_id` должен совпадать с этим UUID.
Адаптер возвращает сам IPv4 как идентификатор назначения, поэтому
`initial_allocation_id` должен совпадать с `initial_ip`.

Один раз открой отдельный профиль Chromium от имени той же учётной записи,
которая будет запускать контроллер, и войди в 1Cent обычным способом. Для
этого нужен доступ к графическому сеансу на машине контроллера. Установи
Playwright в виртуальное окружение и Chromium для этой учётной записи,
затем используй тот же Python в командах адаптера:

```sh
python -m pip install playwright
python -m playwright install chromium
python -m spn_ip_failover.onecent --config /etc/spn-ip-failover/onecent.json login
```

Для операций `check`, `inventory`, `allocate`, `release` и `retire` задай команду
`["/path/to/venv/bin/python","-B","-m","spn_ip_failover.onecent"]`. Файл
конфигурации передаётся через `ONECENT_CONFIG` или аргумент `--config`.
Сначала проверь список и котировку без заказа:

```sh
printf '%s\n' '{"operation":"quote","server_id":"UUID_УСЛУГИ"}' |
  python -m spn_ip_failover.onecent --config /etc/spn-ip-failover/onecent.json
```

Адаптер сверяет количество и обе суммы ещё раз перед кнопкой «Заказать».
Выдача подтверждается появлением ровно одного дополнительного IPv4 в двух
чтениях. Для неопределённого заказа используй `reconcile` с теми же полями,
что для Xorek, и затем сверь журнал контроллера. При заданных `ONECENT_EMAIL`
и `ONECENT_PASSWORD` адаптер восстанавливает вход через проверенную форму.
Если кабинет запросит CAPTCHA, одноразовый код или другой дополнительный
шаг, требуется ручной `login`. После неподтверждённого входа действует
пауза пять минут до следующей попытки.

В основном инвентаре сервера 1Cent укажи `release_initial: true`. После
подтверждения работы нового IPv4 контроллер освобождает отклонённые покупки
и ждёт заданный период DNS. Когда в кабинете остаются старый главный и
новый дополнительный адрес, операция `retire` удаляет старый и проверяет,
что новый стал главным. Повтор запроса после успешного удаления сверяет
список адресов.

Обычная очистка освобождает дополнительные IPv4, купленные адаптером, и
адреса, явно указанные в `removable_existing_additional_ipv4`. Если
интерфейс потребует отдельного неподтверждённого действия удаления,
адаптер остановит очистку до сверки в кабинете.
