# Voxa Fleet: план автоматизации SPN

Дата исследования: 17 ноября 2026. Статус: технический план, не запущенная программа.
Покупки, удаления VPS, создание ключей и переключение контроллера не выполнялись.

## Коротко

Контроллер на `185.9.24.53` сможет создавать VPS по запросу, проверять VPN,
заменять неисправные адреса через новую VPS и сохранять прежний сервер в Remnawave.
Но SSH-проверка не равнозначна проверке VPN и не доказывает блокировку по всей РФ.

Два уже написанных скрипта — основа установки, а не готовый Linux-контроллер:
проверки сейчас привязаны к Mac. Их надо вынести в общий движок и добавить Linux.
Программу 1CENT не переделываем заменой названия провайдера: у Voxa другой API,
биллинг и жизненный цикл целой VPS, а не дополнительного IP на прежней VPS.

## 1. Что подтверждено в Voxa API

Первичные источники:

- [Руководство Customer API](https://my.voxa.host/api/v1/guide.md).
- [Машиночитаемый OpenAPI](https://my.voxa.host/api/v1/openapi.json).
- [Справочник](https://my.voxa.host/api/v1/docs).
- [Обзор и ограничения](https://voxa.host/dedicated-server-api).
- [Тарифы VPS](https://voxa.host/vps).

Прочитана публичная документация без ключа и авторизации. API — beta; в полученной
спецификации 90 операций. Наличие кнопки API в кабинете само по себе недостаточно:
для каждой денежной операции используем именно документированный контракт.

| Задача | Подтверждённый интерфейс |
| --- | --- |
| Проверить ключ, права и проект | `GET /` |
| Узнать баланс и расходы | `GET /account/balance`, `/account/usage`, `/account/transactions` |
| Получить тарифы и доступность | `GET /products`, `/products/{id}/availability` |
| Заказать VPS | `POST /orders`, цикл `hourly`, постоянный `Idempotency-Key` |
| Найти заказ после обрыва | `GET /orders` с `idempotencyKey` |
| Узнать готовность VPS и IP | `GET /vps/{serviceUUID}`, `/vps/{id}/ips` |
| Удалить немедленно | `POST /services/{id}/cancel`, `immediate: true` |

ID услуги из заказа должен однозначно связывать заказ, новую VPS и её IP.
Статус оплаты и состояние машины — разные поля: оплаченный заказ ещё не означает,
что гостевая ОС загрузилась. Проверяем готовность машины и назначенный IPv4.

Заказы поддерживают идемпотентность. Повтор использует тот же ключ и неизменное
тело; другой ключ — это другая покупка. После неопределённого ответа сначала
восстанавливаем результат заказа. Почасовая покупка расходует кредит; не надо
добавлять к ней отдельную оплату счёта. API-песочницы нет: тестовый заказ настоящий.

Обычная отмена может означать конец оплаченного срока. Для немедленного удаления
явно передаём `immediate: true` и подтверждаем итоговое состояние услуги.
Выключение питания не равно прекращению оплаты. Во время установки удаление может
быть недоступно: незавершённый кандидат остаётся в учёте и бюджете до выяснения.

### Неподтверждённая часть

В полной опубликованной спецификации не найден метод замены основного IPv4,
включая первую бесплатную замену. Методы чтения списка IP не являются заменой.
Неизвестны её API-контракт, условия бесплатности и последующая цена.

До ответа поддержки эту ступень нельзя объявлять автоматизированной. Варианты:
ручной шаг с ожиданием подтверждения либо отдельно согласованный пропуск этого
шага и пересоздание VPS в пределах бюджета. Не подменяем API кликами по кабинету.

Также уточнить минимальный кредит, округление коротких аренд, расчёт при
неудачном создании и допустимость частого пересоздания. Не рассчитывать на
возвраты по правилам 1CENT. В API есть поля принятия условий/отказа от права
отмены; такие согласия нельзя принимать молча — они согласуются до автопокупок.

## 2. Что означает проверка из России

`185.9.24.53` — одна российская сеть, не вся Россия и не конкретный МегаФон,
МТС или домашний провайдер пользователя. Доступность с неё может отличаться
от мобильного оператора. В интерфейсе пишем «недоступен из контрольной сети РФ»,
а не «доказанно заблокирован во всей РФ».

Проверять SSH можно без пароля: TCP22, SSH-баннер и при необходимости начало
обмена протокола. Ждать текст приглашения пароля не надо: при входе только по
ключу его вообще может не быть. Для управления используем отдельный SSH-ключ.

### Уровни проверки

1. **Контроль измерителя:** есть ли интернет на RF-контроллере и доступны ли
   несколько независимых контрольных HTTPS-адресов. При проблеме измерителя
   результат `unknown`, расходы запрещены.
2. **Сеть:** TCP22 и TCP443 до выбранного IP, DNS отдельно. Не обращаемся к
   домену через FakeIP/системный VPN и не называем SSH-туннель прямой проверкой.
3. **Настоящий VPN:** отдельный Xray-клиент с теми же REALITY/Vision/SNI,
   аутентификация, HTTPS через VPN, ожидаемый выходной IP. Нет DIRECT fallback.
4. **Независимая внешняя точка:** тот же VPN проверяется вне РФ. Для неё нужен
   подтверждённый, принадлежащий пользователю узел; не покупаем его без согласия.
   Уже существующий EU-сервер можно использовать ограниченным проверочным агентом.
5. **Подтверждение:** несколько последовательных раундов, а не один timeout
   и не значение пинга из приложения.

| Наблюдение | Действие программы |
| --- | --- |
| VPN работает, SSH не отвечает | Проблема управления; VPS не покупать |
| SSH работает, VPN не работает ни из РФ, ни извне | Проверить ноду/конфигурацию/нагрузку; не объявлять блокировку |
| VPN не работает из РФ, работает извне, контрольные проверки исправны | После повторных раундов разрешён поиск замены |
| Не работают контрольные адреса или внешний измеритель | `unknown`, пауза, уведомление; без покупок |
| Разные российские точки расходятся | Частичная недоступность; следовать явно выбранной политике, не считать всю РФ заблокированной |

Начальное предложение: лёгкая проверка раз в 30 секунд, три плохих раунда для
подтверждения, ограниченные таймауты и более редкий полный тест загрузки.
Это настраиваемая политика, не обещание смены IP ровно за 90 секунд: загрузка
новой VPS, установка и DNS занимают дополнительное время. При одновременном
отказе всей группы — сначала один кандидат, не массовые заказы для всех серверов.

Нужен минимум один исправный измеритель РФ и один независимый внешний.
Пустой список измерителей или устаревший результат не считается успехом.

## 3. Постоянный сервер и временная VPS — разные сущности

**Логический сервер** хранится постоянно:

- внутренний ID и понятное имя;
- домен вроде `nl1.wayspn.com`;
- UUID ноды, хоста, профиля и инбаунда Remnawave;
- REALITY-ключи, short ID, настройки и доступные сквады;
- ID зоны и **прежней** A-записи Cloudflare;
- разрешённый тариф/локация, бюджет и режим мониторинга.

**Физическое размещение** меняется:

- UUID заказа и ID VPS/услуги Voxa;
- IPv4 и SSH-ключ самой новой машины;
- время создания, готовность, стоимость, статус удаления;
- уникальное имя заказа, номер поколения и связь с логическим сервером.

Не используем один и тот же hostname заказа для всех поколений: постоянным
остаётся публичный домен клиентов, а hostname машины/заказа должен быть уникальным.

Идентичность не устанавливается по IP, красивому имени или разнице списков VPS.
Связь доказывают сохранённая операция, заказ и возвращённый ID услуги. Ручные VPS
в том же аккаунте не мешают программе: она их не трогает без отдельного импорта.

## 4. Алгоритм замены

1. Проверить, что сервер явно добавлен в управление, режим разрешает замену,
   измерители исправны, нет чужих изменений и другой операции этого сервера.
2. Зафиксировать причину, UUID, прежнюю VPS, DNS и финансовый резерв в журнале.
3. Проверить каталог, наличие нужной локации и предел цены. Создать **один**
   почасовой заказ с постоянным ключом идемпотентности.
4. Дождаться выдачи VPS, IP и готовности ОС. При неясном ответе не покупать ещё
   одну машину. Отдельно учесть ошибку создания и ещё тарифицируемые кандидаты.
5. Подтвердить новую машину, выполнить быстрые сетевые проверки и установить
   ноду без новых объектов Remnawave. Передать прежние ключи только по защищённому
   административному каналу. Текущее публичное DNS пока не менять.
6. Для получения прежней конфигурации временно направить управление **той же**
   нодой на числовой IP кандидата. Прежние UUID, имя, профиль и хост не менять.
7. Проверить настоящий VPN на новом IP из РФ и извне. SSH22 — только отдельный
   диагностический сигнал, не разрешение на публикацию.
8. Если кандидат плохой: сначала вернуть согласованное состояние управления и
   записать отказ кандидата. Проверить точный ID перед удалением, подтвердить его
   удаление и расчёт расходов. Только затем следующая попытка/ручная смена IP.
9. Если кандидат хороший: изменить **content прежней A-записи** Cloudflare,
   сохранив ID, домен, DNS-only и TTL. Чужие записи не создавать и не удалять.
10. Дождаться авторитетного/рекурсивного DNS и старого TTL, вернуть адрес
    управления нодой на домен. Проверить выгрузку подписки и реальный VPN ещё раз.
11. Зафиксировать новое активное поколение. После контрольного периода и повторной
    проверки удалить прежнюю управляемую VPS, если она ещё существует.

Предпочтительный порядок — сначала рабочая замена, потом удаление старой VPS.
На время переноса возможна оплата двух машин. Если старую VPS уже удалили вручную,
перенос всё равно возможен по сохранённым ключам; автоматического отката на неё нет.

Активные TCP-соединения при смене VPS оборвутся; возможны переподключение клиента
и задержки DNS-кэша. Подписку менять/импортировать заново не нужно. Если клиент
использует старую IP-only конфигурацию вместо домена, это отдельная миграция.

## 5. Ошибки и перезапуск программы

Главная доработка к нынешнему `replace.py`: неудачный кандидат не должен навечно
привязывать операцию к одному `toIp`. Нужны явные состояния отказа/завершения
кандидата и согласования промежуточных DNS/Remnawave перед следующей попыткой.
Нельзя решать это удалением папки журнала.

Жизненный цикл кандидата:

`reserved → ordered → provisioning → bootstrap → vpn-tested → cutover → committed → old-retired`

Отдельные ветки: `rejected`, `cleanup-pending`, `outcome-unknown`, `manual-review`.
Они не являются успешным завершением. Пока неизвестно, был ли заказ или удаление,
денежные повторы и новый кандидат запрещены.

Нужны журнал/очередь с транзакциями и одним владельцем операции на логический
сервер. Для панели и фонового исполнителя подходит SQLite с WAL и устойчивым
журналом операций. Сеть не вызывается внутри длинной DB-транзакции: сначала
надёжно записывается намерение, затем запрос, затем сверенный результат.

После рестарта читаем журнал и реальное состояние Voxa/DNS/Remnawave, а не
считаем последний незаписанный шаг ни успешным, ни неуспешным. Повторные ручные
кнопки и Telegram-команды получают тот же ID операции и не создают новые заказы.

Если DNS уже переключён, а финальная проверка не прошла, программа не удаляет
единственную новую VPS и не возвращает DNS на заведомо удалённую старую. Нужны
проверенный откат при живой старой VPS либо контролируемое продолжение переноса.

## 6. Ограничение расходов и удалений

Старые лимиты 1CENT (рубли за дополнительные IP) не переносим на почасовые VPS
автоматически. До отдельного согласования Voxa-расходов автопокупки выключены.

Согласовать и хранить явно:

- допустимые productId, локации, ресурсы, скорость порта и почасовую цену;
- валюту, налоги/локационную надбавку, суточный лимит новых расходов;
- потолок текущей почасовой стоимости всей группы и минимальный резерв баланса;
- число попыток на инцидент и максимум одновременно живых кандидатов;
- контрольный период перед удалением старой VPS и критерий неудачной попытки.

Как безопасные начальные предложения: один кандидат за раз, до двух VPS на
логический сервер на время переноса, не более 10 попыток на инцидент и ранняя
пауза при повторении одной проблемы. Это **предложения**, не разрешение тратить.

Возврат/удаление не восстанавливает автоматически дневной лимит заказов. Помимо
реальных списаний учитывать резерв, минимальные периоды аренды и продолжающуюся
стоимость всех не удалённых VPS. Отмена, зависшая на стороне провайдера, не
считается бесплатной. Когда баланс/бюджет/стоимость неизвестны — уведомление,
а не новая покупка. Нехватка API-кредита не должна провоцировать цикл заказов.

Удалять можно только точный ID VPS этой операции/старого управляемого поколения,
не активное поколение другого сервера, не контрольный EU-узел, не контроллер и
не вручную купленную чужую VPS. Проверка проекта и владения повторяется перед
запросом удаления. Нельзя удалять всё, чего нет в последнем ответе списка.

## 7. Ключи и защита

Создать отдельный проект Voxa для автоматизации и привязать к нему API-ключ;
IP allowlist — `185.9.24.53`. Проект ограничивает видимые ресурсы, но не выделяет
отдельный баланс: локальные лимиты расходов всё равно обязательны.

Начать с отдельного read-only ключа для изучения аккаунта/каталога. Для покупок
потребуются `orders`, для удаления `destructive`; `services` — если используем
управление/переустановку. `billing` не включать только ради почасовых заказов:
им не нужна отдельная оплата счёта. Нужные права подтвердить на выбранном тарифе.

Финансовые/удаляющие права получает исполнитель, не браузер и не проверочный
Xray-процесс. Секреты не уходят в URL, argv, логи, cloud-init, шаблон VPS или
ответы панели. Настройка — защищёнными файлами/systemd credentials, без передачи
в чат. Код работает под отдельным пользователем, не постоянным root.

На RF-контроллере хранение Cloudflare/Remnawave/Voxa секретов увеличивает ущерб
при взломе. Перед переносом нужен явный выбор этих прав и защищённая резервная
копия состояния. Одного ограничения ключа по IP недостаточно для защиты самого
скомпрометированного контроллера. Система не должна выдавать ключи через панель.

Для первого SSH-входа автоматизация не должна просто принимать любой `keyscan`.
Предлагаемый способ: публичный ключ управления и короткоживущий одноразовый
bootstrap-идентификатор в заказе; новая VPS через TLS подтверждает свой ID/IP и
SSH host key. Подтверждение связывается с конкретным заказом и ожидаемым IP.
Другой вариант — проверяемый host key, предоставленный доверенным API, если
Voxa его поддерживает. Этот механизм требуется проверить платным пилотом.

В cloud-init не передавать долгоживущие инфраструктурные ключи. Если используем
готовый образ, он не должен содержать прежние SSH host keys, machine-id,
Remnawave secret, REALITY-ключи, маркеры установки и старые IP/маршруты.

## 8. Панель управления

Панель полезна: она показывает, **почему** программа решила заменять сервер и
сколько это стоит. Она не улучшает сетевую доступность сама по себе.

Первый экран — список серверов: имя, домен, активный IP/ID VPS, VPN из РФ,
VPN извне, SSH, состояние ноды, режим, текущая операция и последняя замена.
Отдельно: баланс, текущая цена в час, расходы/резерв за сутки и оставшийся лимит.

Карточка сервера:

- история проверок с причинами и временем, не только зелёный/красный кружок;
- кнопки «Проверить», «Заменить», «Пауза», «Продолжить операцию»;
- действующий и неудачные кандидаты, статус их удаления;
- домен, сохранённые UUID и локация; без отображения секретов;
- режим «только наблюдение / подтверждать покупки / автоматический».

«Создать сервер»: имя, свободный домен, разрешённая страна/локация, тариф и
сквады. Перед покупкой — цена, период и возможные надбавки. После создания
сервер появляется в той же программе и Remnawave, мониторинг по выбранному режиму.
Количество/каталог/цены берутся из API, не из старого скриншота сайта.

Аварийные действия: «Остановить новые покупки» не удаляет VPS и не прерывает
запись уже начатой операции; «Остановить замену этого сервера» тоже не равнозначно
удалению кандидата. Удаление — отдельное действие с указанием ID и последствий.

Первую панель безопаснее открыть через SSH-туннель, без публичного админ-порта.
Для постоянного публичного доступа — HTTPS и сильная аутентификация/2FA,
защита сессий и действий, а не секретная ссылка. Telegram — уведомления об
инциденте, цене/замене и необходимости решения; покупки не запускаются из
непроверенного текста сообщения. Подключение бота отдельно согласуется.

## 9. Этапы реализации

1. **Только чтение.** Проверить ключ/проект, каталог, цены, ID существующих VPS,
   текущую готовность RF/EU-проверок и выбранный список логических серверов.
2. **Общий Linux-движок.** Переиспользовать проверенные установщик, сохранение
   UUID/ключей и DNS, заменить Mac-зависимости; добавить отказ/очистку кандидатов.
3. **Сухой контроллер.** Он наблюдает и объясняет будущие решения/цену, но
   создающие/удаляющие вызовы отключены. Ошибка измерителя не означает блокировку.
4. **Один отдельно согласованный платный пилот.** Ограничить цену одного заказа,
   проверить реальный заказ, перезапуск программы, отбраковку кандидата, перенос
   прежних UUID, DNS и реальный VPN, а также удаление точного тестового ID.
5. **Ограниченный автомат.** Один выбранный сервер и утверждённые бюджеты;
   затем расширить управляемый список. Переключить службы 1CENT только после
   проверки состояния: два финансовых контроллера одновременно не запускать.
   Старые журналы/ключи 1CENT не уничтожать вместе с отключением службы.
6. **Панель.** Тот же внутренний API и очередь операций; не отдельная логика
   покупок, которая может обойти ограничения исполнителя.

Быстрее всего получить полезный результат через наблюдение и ручной запуск
замены из программы. Сразу включать бесконтрольный автомат на всю группу нельзя.

## 10. Проверки до запуска денег

- Таймаут после принятого заказа, повтор кнопки и рестарт не создают дубликат.
- Изменение тела заказа с прежним ключом не принимается за новую конфигурацию.
- DNS и ключи прежние; нет POST-создания новых объектов Remnawave при замене.
- Неудачный кандидат закрывается и позволяет следующий без удаления истории.
- Провал контроля/SSH внешнего измерителя, отказ API и устаревшие результаты
  не вызывают покупки; пустые списки измерителей отвергаются.
- Рабочий SSH при заблокированном VPN443 не признаётся рабочим сервером.
- Удаляется только принадлежащий операции ID; ручная/чужая VPS сохраняется.
- Рестарт после DNS и до финальной проверки не удаляет единственную новую VPS.
- Смена человеком домена, конфигурации или активной VPS обнаруживается до
  следующей мутации. У каждой долгой операции ограничены время и число повторов.
- Исчерпание бюджета/баланса, изменение цены, API429 и незавершённое удаление
  останавливают новые заказы; после перезапуска бюджет не обнуляется.
- Полный Linux-тест подтверждает VPN по публичному пути без SSH/VPN-подмены.
- При потере самого RF-контроллера остаются закрытые резервные копии состояния
  и возможность ручного управления через Voxa/Remnawave/Cloudflare.

## Что требуется согласовать перед реализацией платной части

1. Ответ Voxa о бесплатной смене основного IP и её API; точные условия расчёта.
2. Разрешённые тарифы/локации, предел цены, бюджет и число кандидатов.
3. Список серверов под автоматизацией и независимая EU-точка проверки.
4. Права/хранение ключей, необходимые согласия при заказе и лимит одного пилота.

До этого можно писать и тестировать код на поддельных ответах, а с read-only
ключом изучать реальные цены и аккаунт. Заказывать/удалять что-либо для
«исследования API» не требуется и в этом исследовании не выполнялось.
