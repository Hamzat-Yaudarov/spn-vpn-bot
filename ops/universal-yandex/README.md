# Установщик Яндекс CDN XHTTP

Новая отдельная VPS → HTTPS origin → вручную созданный Яндекс CDN → один
хост Remnawave. Настройки XHTTP взяты с проверенного хоста
«🇩🇪 Германия • ОБХОД 1»: `packet-up`, **GET/header**, TLS / HTTP2 / Firefox.
Оригинальный хост, другие серверы и пользователи не изменяются.

Скрипт **не покупает и не создаёт ресурсы Яндекса**. В консоли ты самостоятельно
создаёшь сертификат и один CDN-ресурс. Установщик после подготовки выдаёт
подробную персональную инструкцию со всеми значениями, настройками и командами
продолжения; та же инструкция сохраняется в приватный Markdown-файл.

## 1. Подготовка VPS одной командой на Mac

Нужна **чистая Ubuntu 24.04**, отдельная от существующих VPN. Старую ноду
скрипт не удаляет и не преобразует автоматически. Публичный IPv4 должен быть
назначен самой VPS; входящие TCP 22/80/443 должны быть доступны снаружи.
TCP 2222 открывается в ОС только IP панели; 10085 остаётся на loopback.

Используются прежние настройки API Remnawave из `.env` проекта и сохранённый
токен Cloudflare: Zone DNS Edit + Zone Read только для нужной зоны. Токены
не передаются на VPS. Если Cloudflare ещё не настроен:

```bash
python3 ~/Downloads/SPNvpnF/ops/universal-reality/setup_cloudflare.py
```

Установка:

```bash
python3 ~/Downloads/SPNvpnF/ops/universal-yandex/deploy.py \
  --ip НОВЫЙ_IP \
  --name "🇩🇪 Германия" \
  --country DE \
  --squad bypass \
  --keep-tcp-port 10050 \
  --agree-le-tos \
  --apply
```

Замени `НОВЫЙ_IP` адресом новой VPS. Сквад можно изменить или убрать `--squad`,
чтобы выбрать его из меню. `--keep-tcp-port 10050` — **явное разрешение оставить
TCP 10050 открытым**, не определяя тип службы хостинга и не трогая саму службу.
Если это не нужно, убери параметр: распознанный штатный Zabbix допускается
автоматически, неизвестная служба — нет.

`--agree-le-tos` подтверждает выпуск бесплатного сертификата origin и условия
Let's Encrypt. Это не согласие на покупку CDN.

Домены создаются автоматически:

- `origin-yc-<код>.wayspn.com` — DNS-only A на IP VPS;
- `cdn-yc-<код>.wayspn.com` — будущий адрес CDN, пока без записи.

Можно заранее выбрать свои **два разных свободных поддомена**:
`--domain de-yc-origin.wayspn.com --cdn-domain de-yc.wayspn.com`.
Для другой зоны добавь `--dns-zone example.com` и токен с её правами.
Чужие существующие DNS-записи не принимаются во владение и не затираются.

Имена профиля, inbound, ноды и хоста получают случайный шестизначный код.
Повторный запуск той же установки сохраняет UUID и ключ службы, не создаёт
дубликаты и не повторяет POST с неизвестным исходом.

## 2. Выполни выданную персональную инструкцию

Когда origin готов, скрипт напечатает подробный документ **«Ручное подключение
Яндекс CDN»** и путь к его `.md`-копии. Не используй значения от чужой установки.

Последовательность в документе:

1. В Certificate Manager вручную создай сертификат для нового CDN-домена.
   Выбери **DNS_CNAME**, скопируй его CNAME-цель.
2. Выполни выданную команду с `--certificate-target`: установщик добавит
   `_acme-challenge.CDN_DOMAIN` в Cloudflare. SSH-пароль на этом шаге не нужен.
   Дождись `Issued`. Проверочный CNAME не удаляй — он нужен для продления.
3. Вручную создай **один** CDN-ресурс. Все конкретные поля указаны в документе:
   HTTPS origin, собственные origin Host и SNI, отдельный CDN-домен, выбранный
   сертификат, отключённые кеширование/сжатие/сегментация/логи/экранирование.
   Используется GET/header — не POST и не GET с телом.
4. Скопируй выданную ресурсом CNAME-цель и выполни команду с `--cdn-target`.
   Установщик создаст второй DNS-only CNAME. Origin A останется на VPS.
5. После распространения сертификата/DNS выполни выданную команду
   **`--finish --apply`**.

Это разные записи: A источника, CNAME раздачи и CNAME подтверждения сертификата.
Не включай оранжевое облако Cloudflare и не направляй origin обратно на CDN.

Перед платным подтверждением в Яндексе проверь фактическую стоимость в консоли:
кроме пакета возможна оплата перерасхода и дополнительных функций. Этот скрипт
не совершает платные действия. Инструкция сверена с официальными материалами:
[создание CDN](https://yandex.cloud/ru/docs/cdn/operations/resources/create-resource),
[методы HTTP](https://yandex.cloud/ru/docs/cdn/operations/resources/configure-http),
[проверка сертификата](https://yandex.cloud/ru/docs/certificate-manager/concepts/challenges),
[origin SNI](https://yandex.cloud/ru/docs/cdn/operations/resources/configure-server-name),
[тарифы](https://yandex.cloud/ru/docs/cdn/pricing).

## 3. Что проверяет `--finish`

Нужна прежняя действующая проверочная подписка в `.vpn-test-link.txt` с правами
0600. Пользователь этой подписки должен иметь доступ к выбранному скваду.
Новые подписки и пользователи не создаются; выполняется несколько запросов
через уже оплаченную/действующую подписку, включая 1 МиБ тестовых данных.

Скрипт повторно проверит VPS и отдельный origin, TLS CDN и согласование HTTP/2,
запустит изолированный XHTTP-клиент без DIRECT-fallback и выполнит **9 реальных
VPN-запросов** через CDN, в том числе проверку внешнего IP и параллельные запросы.
Затем ненадолго включит свой хост и проверит его фактическую выгрузку в подписке.
Если экспорт неверен, только что включённый хост вернётся в выключенное состояние.
Изменённые вручную технические параметры хоста не перезаписываются. Если ранее
проверенный хост выключен владельцем, повторный успешный тест не включает его.

TLS, Host и точный `/health` origin проверяются **на самой VPS через доверенный
SSH**. Подготовка не требует прямого HTTPS-доступа с Mac к IP origin: этот путь
может быть заблокирован в РФ. Локальная проверка origin не подтверждает путь
Яндекс → origin; его проверяют CDN TLS/HTTP2 и настоящий VPN на `--finish`.

Сам по себе ответ `/health`, код 400 на незавершённый запрос или пинг не считается
успехом VPN. До настоящей проверки новый хост остаётся выключенным.

По умолчанию клиент проверки привязывается к физическому `en0` Mac Apple Silicon.
Для другого физического интерфейса укажи `--interface en5`. `--test-route system`
явно допускает текущий VPN Mac и **не доказывает прямой доступ** к CDN без него.
Доступность во время белых списков проверяется отдельно в сети оператора:
универсальной гарантии обхода или постоянной доступности IP нет.

## Повтор, переустановка и границы

Если origin DNS переведён на дополнительный адрес той же VPS, Nginx также
должен принимать HTTPS на этом адресе. `origin_bindings.py` добавляет один
отдельный vhost после проверки исходных хешей, назначения обоих IP и полного
`nginx -t`; при неудачной проверке HTTPS удаляет только новый symlink и
перечитывает исходную конфигурацию. Основной vhost, сертификат, параметры
установки и `files.sha256` сохраняются. Подтверждённая локальная квитанция
`origin-bindings.receipt.json` позволяет последующим проверкам читать текущую
DNS-запись по прежнему ID, сохраняя дополнительный vhost. Чужие конфигурации,
неизвестные symlink и несовпадающие квитанции автоматически не принимаются.

После ошибки подготовки повтори исходную команду. После готовности origin
обычный повтор показывает инструкцию и обрабатывает переданные CNAME без SSH.
Для повторной проверки/восстановления **своего** origin после переустановки той
же VPS добавь `--recheck-origin --agree-le-tos`; изменившийся SSH-ключ потребует
явного подтверждения. Для переноса на совершенно новую VPS используется
отдельный `replace.py`; изменение дополнительного IP на прежней CDN VPS пока
не автоматизировано.

## Полная замена CDN VPS

После завершённого `--finish` можно перенести тот же origin на чистую Ubuntu
24.04, сохранив клиентский CDN-домен, origin-домен, UUID ноды/профиля/инбаунда/
хоста, сквады и приватный XHTTP path. Новый CDN-ресурс или сертификат в Яндексе
создавать не требуется. Ресурсы Яндекса и обе их CNAME-записи не изменяются.

```bash
python3 ~/Downloads/SPNvpnF/ops/universal-yandex/replace.py \
  --domain ИСХОДНЫЙ_ORIGIN_ДОМЕН --ip НОВЫЙ_IP \
  --state-dir КАТАЛОГ_ИСХОДНОЙ_CDN_УСТАНОВКИ \
  --test-route system --interface lo --apply
```

Команда предназначена для VPS-контроллера и требует прежний SSH-порт,
закреплённое SSH-доверие/ключ, настроенный API-токен панели, Cloudflare-токен,
проверочную подписку, `certbot`, `openssl`, `dig` и поддерживаемый проверочный
Xray. Пароли и API-токены интерактивно не запрашиваются. На Mac вместо `lo`
укажи подходящий интерфейс; `system` проверяет текущую сеть запускающего узла.

Сначала через DNS-01 выпускается отдельный сертификат origin; Cloudflare-токен
остаётся на контроллере. На новой VPS сертификат импортируется со своим ACME
account и HTTP-01 webroot для дальнейшего `certbot.timer`. После установки
проверяются HTTPS origin, исходящий IP и **9 настоящих VPN-запросов напрямую
через новый origin**. Только после этого обновляется существующая origin A.
Затем проверяются DNS/TTL, **9 VPN-запросов через прежний CDN** с новым выходным
IP и прежняя выгрузка подписки. До всех этих подтверждений операция остаётся
незавершённой. Кэш origin у CDN может обновляться дольше обычного DNS TTL.

Старая VPS не удаляется. При ошибке повтори ту же команду с тем же IP: журнал
сохранит этап, а другая цель не затрёт незавершённую операцию. После cutover
автоматического отката DNS нет. Проверь подключение клиента перед удалением
прежней VPS. Если CDN настроен на числовой IP вместо origin-домена из исходной
инструкции, финальная проверка остановится: исправь источник своего CDN-ресурса
и продолжи ту же операцию.

Сохрани защищённую резервную копию `~/.spn-yandex-deploy/`. Внутри есть ключ
службы ноды и собственные квитанции операций; не публикуй этот каталог или
ссылку проверочной подписки. Сеть/SSH не перезапускаются, нет глобального
IP-forward/NAT; Nginx перечитывается после проверки конфигурации. Лимиты Nginx
подняты до 8192 соединений на worker и 65535 файлов.

Без `--apply` выполняется только локальный план, без сети/записей/платежей.
Локальные проверки:

```bash
python3 -m unittest discover -s ~/Downloads/SPNvpnF/ops/universal-yandex -p 'test_*.py'
```

Новый CDN/VPS в рамках разработки этого установщика не создавался и не оплачивался.
