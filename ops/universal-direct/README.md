# Автоматическая установка gRPC и WS

Запускать **на Mac**, не на VPS. Скрипт настраивает новый сервер, создаёт в
Remnawave отдельные профиль, ноду, два хоста и добавляет инбаунды в выбранные
сквады. Рабочие ноды и существующие подписки не переустанавливает.

## Один запуск

1. Нужен **чистый Ubuntu 24.04**, публичный IPv4 на интерфейсе VPS и доступ root
   по SSH. Это установщик чистого сервера, не инструмент изменения сетевых
   настроек уже работающей VPS.
2. Создай DNS-запись **A**, например `de-new.wayspn.com` → новый IP, **DNS only /
   серое облако**. У этого имени не должно быть AAAA-записи. Дождись обновления DNS.
3. В терминале **Mac** выполни:

   ```sh
   python3 ~/Downloads/SPNvpnF/ops/universal-direct/deploy.py \
     --ip НОВЫЙ_IP \
     --domain de-new.wayspn.com \
     --name "🇩🇪 Германия" \
     --country DE \
     --apply --agree-le-tos
   ```

Замени `НОВЫЙ_IP`, домен и название. `DE` — код страны для ноды, например
`FI`, `EE`, `SE`, `PL`; этот параметр можно вообще убрать. Нестандартный SSH-порт
задаётся `--ssh-port 22222`.

Скрипт многоразовый: для каждого нового сервера меняй IP, домен, название и код
страны. Например, для Финляндии — `--country FI`, для Германии — `DE`.
Новый IP или домен автоматически получает отдельное состояние и новые панельные
объекты. Остановленный старый запуск этому не мешает и не перезаписывается.
Тот же домен можно переиспользовать после замены VPS, обновив A-запись; один
домен не направляет трафик одновременно на две разные VPS. Старые профили,
ноды и чужие хосты скрипт автоматически не удаляет и не перенастраивает.

Если macOS возвращает `::ffff:НОВЫЙ_IP`, проверка пропустит его: это представление
того же IPv4, не отдельная AAAA-запись. Другой IPv6 по-прежнему остановит установку;
сообщение покажет найденный адрес, не объявляя его автоматически записью DNS.

Скрипт предложит выбрать сквады и запросит пароль SSH, если вход по ключу не
настроен. Новый SSH-ключ сверяй с отпечатком из консоли хостера. Изменившиеся
ключи скрипт не удаляет и проверку сервера не отключает.

Если ОС переустановлена, но **IP и домен остались прежними**, добавь `--reinstall`:
установка повторится на чистой VPS, а собственные профиль, нода, хосты и ключ
будут использованы повторно. Повтор без этого флага после успешного завершения
не переустанавливает сервер. Это не отключает проверку SSH-ключа и не даёт
разрешения перезаписывать чужую установку. Параметры прежнего развёртывания
(название, страна, сквады) при таком продолжении должны совпадать с сохранёнными.

Настройки панели берутся из двух полей локального `.env` проекта:
`REMNAWAVE_BASE_URL` и `REMNAWAVE_API_TOKEN`. Если токена нет, появится скрытый
запрос. **Пароль VPS и API-токен не нужно вставлять в команду или переписку.**
API-токен не передаётся на VPS, там сохраняется только служебный ключ ноды.

Для другой панели укажи `--panel-url https://panel.example.com/api`. Её токен
будет запрошен отдельно. Нужен доступ API к профилям, нодам, хостам, ключу ноды
и изменению состава сквадов. Панель должна разрешаться в один прямой публичный
IPv4, без проксирования Cloudflare/CDN.

Чтобы каждый раз не выбирать сквады, добавь `--squad "ИМЯ СКВАДА"`; параметр
можно повторить. Все сквады автоматически не выбираются.

## Что делается автоматически

- Установка Docker, Remnawave Node, Nginx и firewall.
- Выпуск и автоматическое продление сертификата Let's Encrypt.
  `--agree-le-tos` означает принятие [условий Let's Encrypt](https://letsencrypt.org/repository/).
- Отдельный профиль с gRPC и WS, нода и два хоста: `НАЗВАНИЕ • gRPC` и
  `НАЗВАНИЕ • WS`.
- Уникальные стабильные теги инбаундов для каждого развёртывания: существующие
  профили, в том числе с тегами `direct-grpc`/`direct-ws`, не меняются.
- Добавление двух инбаундов в выбранные сквады с сохранением их старого состава.
- Проверка подключения ноды, слушателей, firewall, сертификата и `/health`.
  Хосты создаются выключенными и включаются после этих проверок.

DNS пока создаётся вручную. CDN, платные ресурсы, пользователи, оплаты, лимиты
подписок и баланс не меняются. Состав сквадов во время установки параллельно
не редактируй: API не предоставляет этому скрипту атомарного добавления участника.

После завершения обнови подписку в Happ/INCY и проверь открытие сайтов через
каждый новый хост. Проверка `/health` — это проверка HTTPS/Nginx, **не проверка
VPN-авторизации**. Тестовую подписку скрипт не создаёт.

## Если запуск прервался

Для продолжения повтори **ту же команду с теми же параметрами**. Прогресс и UUID
создаваемых объектов сохраняются локально, раздельно для IP и SSH-порта:

```text
~/.spn-direct-deploy/<идентификатор панели>/<домен>/targets/<IP>-ssh<порт>/
```

Состояние старых версий в каталоге `<домен>/` сохраняется. Оно автоматически
используется только для его прежнего IP/SSH-порта. Новый IP не требует удаления
или исправления старого `plan.json`. Если явно задан `--state-dir`, он остаётся
закреплённым за одной целью: для другой VPS убери этот параметр или выбери новый
отдельный каталог.

Каталог имеет права `0700`, файлы — `0600`. В нём есть служебный ключ ноды,
поэтому храни его как секрет: не коммить, не публикуй и не удаляй для «повтора
с нуля». API-токена и пароля VPS в этом каталоге нет.

Подтверждённые объекты используются повторно. Если ответ на создание потерялся,
но объект появился в панели, скрипт найдёт его по сохранённому намерению. Если
исход операции нельзя установить, запуск остановится **без повторного POST**:
понадобится ручная сверка панели и сохранённого состояния. Хосты распознаются по
сохранённому UUID или UUID собственного инбаунда — совпадение домена/пути не
означает владение. Чужие алиасы не мешают созданию своих хостов и не меняются.
Удалённые объекты и ручные изменения автоматически не перезаписываются.

Если **старая версия** остановилась на `POST /config-profiles` с **HTTP 409**
из-за занятых `direct-grpc`/`direct-ws`, добавь к той же команде
`--recover-profile-conflict`. Это явное разрешение восстановить только этот
незавершённый шаг, не общий обход защиты от повторных запросов. Для таймаута
или неизвестного исхода флаг не используй.

Скрипт проверит отсутствие целевого профиля, ноды и последующих шагов, а также
наличие обоих конфликтующих тегов. Старый intent останется нетронутым, новый
получит отдельную запись восстановления и уникальные теги. Имя профиля
сохраняется — если старый запрос всё-таки создал профиль, второй профиль не
будет создан. После сохранения восстановления следующие повторы продолжают
эту же ветку даже без флага. Уже созданные старые профили продолжают использовать
исходные теги, без изменения работающих подключений.

После успешного завершения повтор той же команды не создаёт дубликаты и не
переустанавливает VPS без `--reinstall`. Новый IP/домен — это новое развёртывание,
не изменение старого. Изменение сквадов, отображаемых параметров или установочного
шаблона внутри уже сохранённого развёртывания требует отдельного обслуживания.
Узкое исключение — исправление чтения UFW: разрешена только одна зафиксированная
пара старого/нового хеша, меняющая исключительно проверку, не правила firewall
или установку. Исходный план сохраняется, рядом записывается маркер обновления
проверки. Это позволяет продолжить после ложного `Panel firewall rule is missing`
из-за комментария `# SPN-PANEL` или формата `ALLOW IN`, не удаляя состояние.

Без `--apply` команда только показывает офлайн-план: не читает токены,
не обращается к сети и ничего не меняет.

## Используемая схема

Оба транспорта используют TLS на Nginx `443`:

- gRPC: `127.0.0.1:10087`, serviceName `spngrpc`.
- WS: `127.0.0.1:10088`, path `/direct/ws/`.
- Управление нодой: `2222`, разрешено только с IPv4 панели.
- SSH, HTTP `80` для сертификата и HTTPS `443` разрешены снаружи.

Это прямая схема TLS из наших новых настроек, **не старый gRPC/REALITY на 2083**.
Версия Node `3.4.1` закреплена digest образа по рабочему шаблону; это не заявление
о том, что она самая новая. Используются маршруты API Remnawave 3.x; при
несовместимом ответе обновлённой панели скрипт останавливается.
Справочники: [API](https://docs.rw/api/),
[установка Node](https://docs.rw/install/remnawave-node/).

Если IPv4 панели изменится, отдельно обнови правило firewall на нодах.

## Проверка локального пакета

```sh
python3 -m unittest discover -s ~/Downloads/SPNvpnF/ops/universal-direct -p 'test_*.py' -v
```

Тесты офлайн: имитируют API и SSH, включая потерянные ответы, повторный запуск,
чужие объекты и ошибку HTTPS перед включением хостов. Они не подключаются к
реальным серверам.

## Старый ручной вариант

`spn-direct-setup.sh` и `profile.json` оставлены для ручной установки. Для нового
автоматического варианта не нужно вручную импортировать JSON, копировать
SECRET_KEY или создавать ноду/хосты. Не запускай оба варианта на одной VPS.
