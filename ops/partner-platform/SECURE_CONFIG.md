# Закрытый тест: конфигурация без секретов в чате

Этап 21.10.2026 завершён: владелец сам задал пароль/LOGIN роли и ввёл секреты на
VPS; owner-private HTTP/manager за HTTPS запущен. Worker/платежи/выдача выключены.
Ниже — порядок первого запуска, **не просьба повторно менять пароли или ключи**.
Актуальное состояние: [VPS_STAGING_STATUS.md](VPS_STAGING_STATUS.md).

## Что ограничено

В основном SPN кнопка **«🚀 Создать свой VPN»** видна только пользователю,
чей положительный Telegram ID совпадает с `ADMIN_ID`. Ограничение действует
и при `/start`, и при возврате в меню; отсутствие ID не считается администратором.
Старый callback постороннему не раскрывает подробности запуска.

Скрытие кнопки — не защита прямой ссылки на бота. Поэтому для стенда есть
отдельный `manager_allowed_user_ids`: `[ваш_ID]` закрывает управляющий бот
и проверенные Telegram API кабинета для остальных. `[]` запрещает всем,
`null` сохраняет прежний открытый режим и **не подходит для закрытого теста**.
Финансовые `operator_ids` не заменяют этот список. Оболочка страницы/ассеты могут
загружаться без входа, но данные и действия посторонним API не выдаёт.
Клиентские боты/личные ссылки подписок не ограничиваются этим списком.

## Активация отдельной роли БД владельцем

При установке схемы отдельного проекта `SPN franchise` роль
`spn_partner_runtime` намеренно создаётся NOLOGIN. На текущем стенде владелец
уже завершил активацию ниже; повторять её или миграции не нужно.
В текущем редакторе существующей роли Supabase есть переключатели привилегий,
но нет поля пароля; на такую форму этот порядок не рассчитывает.

В своём защищённом интерактивном терминале использовать современный `psql` и
session pooler **5432**, не transaction pooler 6543. Для этого pooler системного
набора CA оказалось недостаточно. На VPS установлен публичный Supabase Root
2021 CA из официальной ссылки Download certificate в настройках **SPN franchise**:
`/etc/spn-partner-ca/supabase.crt` (root-owned, 0644; папка 0755).
Системное глобальное доверие не изменено. TLS-проверка цепочки и имени pooler
без аутентификации завершилась `Verification: OK`.

```sh
psql -X -W --set=HISTFILE=/dev/null \
  "host=aws-0-ap-northeast-1.pooler.supabase.com port=5432 dbname=postgres user=postgres.crrmaqiakrqpfvhiwtkq sslmode=verify-full sslrootcert=/etc/spn-partner-ca/supabase.crt"
```

Запрос `Password` относится к **административному паролю БД этого отдельного
проекта**; он вводится скрыто и не сохраняется в runtime-конфигурации. Не
подставлять его в команду, URL, `PGPASSWORD`, переписку или SQL Editor. При
отсутствии этого пароля требуется защищённый доступ владельца к проекту, а не
замена runtime-роли административным логином.

Внутри `psql`:

```text
SET password_encryption = 'scram-sha-256';
\password spn_partner_runtime
ALTER ROLE spn_partner_runtime LOGIN;
\q
```

`\password` дважды скрыто запросит **новый пароль runtime-роли длиной от 16
символов**. Клиент вычисляет SCRAM-верификатор; открытый пароль не попадает в
SQL-команду/историю. Это отдельный пароль, **не пароль VPS и не пароль postgres**.
Меняется только пароль и LOGIN этой роли: не выдавать ей CREATE/DDL, владение
таблицами, административные роли или BYPASSRLS. Настройщик ниже этого не делает.

## Создание root-мастера конфигурации

Установленная версия находится в
`/opt/spn-franchise-staging/releases/20261021-5fab5be5cb97`. После активации роли
владелец запускает в своём интерактивном SSH-терминале с правами root:

```sh
cd /opt/spn-franchise-staging/releases/20261021-5fab5be5cb97
.venv/bin/python scripts/partner_setup.py --config /etc/spn-partner-private/staging.json
```

Потребуются числовой Telegram ID владельца, **уже заданный** пароль
`spn_partner_runtime` и токен **@spn_franchise_bot**. Пароль и токен вводятся
скрыто; никаких секретов в аргументах команд, переписке или скриншотах.
Настройщик не читает основной `.env`, не соединяется с Telegram/Supabase,
не меняет пароль/LOGIN роли и не устанавливает webhook.

Мастер остаётся `root:root`: папка `/etc/spn-partner-private` — **0700**, файл
`staging.json` — **0600**. Настройщик создаёт три независимых ключа и
**не перезаписывает** существующий файл. Символические ссылки, общедоступная
папка, путь в Git вне `.release-secrets`, pipe и открытый ввод пароля запрещены.

Файл остаётся в режиме **disabled**: сеть, записи, оплаты и службы выключены,
для будущего теста допущен только указанный ID. Флаги подтверждения отдельной
БД и отключения Data API не являются удалённой проверкой: до `staging` владелец
проверяет эти условия. Сохранить защищённую резервную копию: потеря/замена ключей
нарушает чтение токенов ботов, реквизитов и личных ссылок. При повторном запуске
используются прежние ключи, а не новый вызов настройщика.

Перед первым `--probe` при подготовке конфигурации записать
`database_ca_file: /etc/spn-partner-ca/supabase.crt` и сохранить
`database_tls: true`. Исходный установленный настройщик оставляет CA-путь пустым:
это выключенный шаблон, не готовое TLS-соединение. Изменение параметра должно
сохранять все уже созданные ключи/токены; не пересоздавать файл настройщиком.
Runtime использует `ssl.create_default_context(cafile=...)` с проверкой имени.

## Передача службе без постоянной копии секретов

Установленные units `spn-partner-http.service` и `spn-partner-worker.service`
по умолчанию выключены и не запущены. При отсутствии root-мастера
`ConditionPathExists` не допускает запуск; конфигурация автоматически не создаётся.

На systemd 247+ `LoadCredential=staging.json:/etc/spn-partner-private/staging.json`
передаёт снимок конфигурации службе, не открывая ей доступ к root-папке.
`ExecStartPre` выполняется как `spn-partner` и копирует те же байты с правами
**0600** в собственный `RuntimeDirectory` с правами **0700**:

- HTTP: `/run/spn-partner-http/staging.json`;
- worker: `/run/spn-partner-worker/staging.json` — пока не запускать.

Runtime проверяет владельца файла по своему UID; поэтому такой временный файл
нужен даже при credential delivery. При остановке каталог удаляется
(`RuntimeDirectoryPreserve=no`). Постоянная service-owned копия не создаётся;
root-мастер и защищённая резервная копия остаются единственными постоянными
источниками. Не решать ошибку чтения через 0644/0777 или раскрытие root-папки.

Службы используют абсолютный путь установленной версии и `User=spn-partner`;
код/venv остаются root-owned. Сохранить `ProtectSystem=strict`, без записи в
`/etc`/release, и постоянное изменяемое состояние только в `/var/lib/spn-partner`.
После изменения мастера работающий процесс сохраняет прежний снимок: нужен
отдельно разрешённый перезапуск соответствующего unit. Ключи при перезапуске
не генерируются заново. У HTTP и worker раздельные снимки конфигурации.

## Минимальный закрытый HTTP/manager-тест

Достаточно согласованного HTTPS hostname для кабинета и manager webhook
(можно одного), DNS/TLS и явного разрешения на staging DB-записи и Telegram
`setWebhook`. Оставить `manager_allowed_user_ids: [ваш_ID]`; включить только
`mode: staging`, подтверждение изоляции, `enable_http`, `enable_manager_webhook`,
`allow_staging_network`, `allow_staging_writes`; заполнить `manager_origin` и
`webhook_origin`. Разрешающие network/write-флаги требуются для HTTP, но сами
по себе не включают платежи или Remnawave.

Billing, provisioning, launches, customer webhooks, public gateway/checkout,
worker и все доставки оставить выключенными. **Пароли/ключи мерчанта и
Remnawave, токен клиентского бота и wildcard DNS для партнёров пока не нужны.**

Сначала `--check` (локально, без сети), затем отдельно разрешённый read-only
`--probe`; выбранный файл должен принадлежать пользователю команды. Только
после успешной проверки — loopback HTTP за HTTPS и явный `--bootstrap-manager`.
Замена обнаруженного чужого webhook требует отдельного согласия. Настоящие
оплаты, публичное включение и рассылки этим этапом не разрешаются.

Эта инструкция обновлена отдельно от уже собранного/установленного архива:
его исходный payload и manifest не изменяются. Актуальный handoff-документ
можно передать на VPS отдельно, не перепаковывая установленную версию.

Для фактической установки использованы проверенные ops-инструменты:
`prepare_private_manager_config.py` (исходная 0600 backup + атомарный переход,
без перегенерации ключей), `prepare_manager_https.py` (существующий аккаунт LE,
один hostname), `run_private_manager_check.py` (непривилегированный transient
probe/bootstrap через credentials). Последний не заменяет чужой webhook и не
запускает HTTP/worker; это отдельные действия. Применение transition и HTTPS
one-shot повторять поверх действующего стенда нельзя.
