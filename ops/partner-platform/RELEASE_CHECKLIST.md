## Отдельный стенд, не перезапуск SPN

`scripts/partner_runtime.py` — независимая точка входа. Она не импортирует
`main.py`, `config.py`, не читает `.env`, не наследует `DATABASE_URL`, не меняет
схему при запуске и не включает режим production/live. По умолчанию только:

```sh
python3 scripts/partner_runtime.py --check
```

Результат `runtime_disabled`, `production_ready: false`; ни сети, ни базы.
Явный JSON должен принадлежать пользователю службы и иметь права 0600.
Начальный пример `runtime.example.json` намеренно пустой и выключенный.
Секреты не передавать в аргументах команд, Git, скриншотах и журналах.
Три независимых ключа: Fernet для токенов/реквизитов, отдельный случайный 32-байтовый
webhook HMAC и отдельный случайный 32-байтовый ключ ссылок подписки. Ключи
нельзя потерять при откате: токены и личные ссылки уже зависят от них.

Ниже — общий порядок для явно переданного service-owned файла, а не команды
текущей установки. На выбранном VPS root-мастер передаётся через systemd
credentials и временную копию `/run`; см. [SECURE_CONFIG.md](SECURE_CONFIG.md).
Проверки/запуск **только после отдельного согласования соответствующего этапа**:

```sh
python3 scripts/partner_runtime.py --config /etc/spn-partner/staging.json --check
python3 scripts/partner_runtime.py --config /etc/spn-partner/staging.json --probe
python3 scripts/partner_runtime.py --config /etc/spn-partner/staging.json --serve
python3 scripts/partner_runtime.py --config /etc/spn-partner/staging.json --worker
```

Для всех франшиз используется **один отдельный от SPN проект Supabase**.
Подготовка проекта, NOLOGIN backend-роли, Data API/RLS и соединения описана в
[SUPABASE_SETUP.md](SUPABASE_SETUP.md). `database_isolation_confirmed` — отдельное
обязательное подтверждение, не синоним тестового мерчанта. Основной `webhooks.py`
вообще не монтирует партнёрские маршруты и не предоставляет им `db.get_pool`.

`--check` проверяет только настройки. `--probe` делает ограниченную read-only
проверку колонок/очередей отдельной базы; это не полное доказательство схемы,
миграций или исправности внешних сервисов. Для Supabase он дополнительно
проверяет server-only роль, RLS/grants и отвергает сигнатуры основной SPN-базы.
Это не заменяет полный аудит нестандартных ролей и Data API. `--serve` слушает
127.0.0.1:8966; журнал URL и доверие произвольным forwarded-заголовкам выключены.
`--worker` делает ограниченные проходы, обрабатывает SIGTERM, после ошибок
увеличивает паузу до 5 минут. Автоматически при старте HTTP он не запускается.

Для HTTP/воркера нужны отдельные явные флаги, подтверждение изоляции и прав
стенда. Реальный мерчант запрещён: адаптер принимает только test mode. Тестовый
мерчант **не делает стенд безопасным для рабочей Remnawave** — нужны отдельные
панель/сквады/боты/домены/база и подтверждение, что это не рабочие клиенты.
Публичные gateway/webhook/уведомления/запуск ботов включаются независимо.
Управление/финансы/брендинг тоже выключены по умолчанию. Финансам дополнительно
нужны список операторов и подтверждённый получатель административных уведомлений.
Три доставки расширений также включаются отдельно: `enable_marketing_delivery`,
`enable_support_delivery`, `enable_finance_notifications`. Ни включение финансов,
ни общие уведомления `enable_notifications` не включают рекламу автоматически.
Маркетинговый воркер берёт только явно подтверждённую рассылку с зафиксированной
аудиторией и повторно проверяет opt-out/блокировку перед отправкой. Воркер
поддержки пересылает уже оплаченную личную подписку только её клиенту, не выдаёт
партнёру сам секрет и не создаёт бесплатный доступ. Финансовые уведомления идут
через центрального менеджера; реальные переводы остаются исключительно ручными.
Каждый hook ограничен таймаутом, ошибки не останавливают другие очереди, сырой
ответ/Telegram ID/URL/реквизиты не попадают в стандартный журнал воркера.

Продление на брендированной личной странице включается отдельным флагом
`enable_public_checkout` (по умолчанию выключен). Он требует одновременно
шлюз, тестовую оплату и durable invoice intent. Разрешено только продление
уже выданной подписки по проверенной tenant-bound личной ссылке; новый веб-аккаунт
не создаётся и с Telegram автоматически не объединяется. Цена показывается
из серверного каталога, изменение до первого счёта требует нового подтверждения.
Потерянный ответ или новая вкладка не создают ещё один счёт по тому же заказу.
Ни открытие страницы, ни сборка runtime счёт сами по себе не создают.

Каталог докупок передаётся явно: отдельный read-only адаптер текущих цен
основного бота либо **только для стенда** проверенный снимок `staging_addon_catalog`.
Снимок — `traffic_packages` с точными рублёвыми `price` и `gb`, `device_rules`
с `price_per_30_days`, `minimum_price`, `discount_step_percent`,
`max_discount_percent`. Значения не выдумываются и не копируются из старой
документации. Пропорциональная цена считается для срока конкретной подписки;
пакеты +1/+2/+3, максимум 10. Без снимка честно показано «цены не загружены»;
`staging_no_addons_confirmed` разрешает только явно выбранную проверку базовой
подписки без докупок. Это **не готовность полноценного каталога к выпуску**.
В web и commerce разные контракты: `catalog_loader()` возвращает исходный
каталог, `addon_loader(subscription, now=...)` — персональную нормализованную
котировку. Не подменять один другим. Снимок не синхронизируется с рабочими скидками.

### Управляющий бот — один явный bootstrap оператора

Важный вход в кабинет — **центральный управляющий бот**, не бот партнёра.
На приватный `/start` он возвращает кнопку «Открыть кабинет» с `web_app`
`manager_origin/partners`; только Telegram этого бота подписывает доверенные
initData. Передавать токен/готовые initData в ссылке нельзя. `/start owner_...`
не выдаёт никаких прав. В партнёрском боте «Админ» ведёт к заранее проверенному
`manager_bot_username`; простая HTTPS-ссылка без запуска MiniApp не авторизует.

`enable_manager_webhook` по умолчанию выключен. Для него нужны отдельный
согласованный username, `webhook_origin`, общий платформенный webhook-ключ,
из которого используется **другое HMAC-пространство** для `/partner-manager/webhook`.
Импорт/старт HTTP/воркера сами webhook не ставят. После запуска изолированного
HTTPS-обработчика оператор отдельно выполняет:

```sh
python3 scripts/partner_runtime.py --config /etc/spn-partner/staging.json --bootstrap-manager
```

Результат `needs_webhook_replace` требует выяснить существующее подключение;
только после явного решения оператора повторить с `--replace-manager-webhook`.
Команда проверяет getMe/username, текущий webhook, ставит неизменный URL/секрет
без удаления pending updates и проверяет read-back. Неизвестный ответ — `retry`,
не доказательство запуска и не повод менять бота/ключ/URL. После bootstrap
вручную проверить приватный `/start` и вход в кабинет; `--check` этого не делает.
Без центрального входа/проверенного username флаг приёма новых оплат не проходит
проверку настройки. В BotFather/кабинете выбранного менеджер-бота также нужно
проверить разрешённый домен MiniApp/кнопки — это отдельная операция владельца.

## До любых миграций

- [ ] Отдельно согласованы тестовый сервер, база и допустимые внешние операции.
- [ ] Проверены адрес/имя БД, пользователь, TLS и отсутствие рабочей SPN-схемы.
- [ ] Data API отдельного партнёрского проекта выключен до создания схемы;
      browser/боты не получают Supabase API keys или пароль БД.
- [ ] Соединение direct или session, не transaction; Supabase project ref
      совпадает, TLS проверяет сертификат/hostname. У сервера достаточно
      соединений для HTTP и worker; отключённый prepared cache сам по себе
      не исправляет несовместимые session locks transaction pooler.
- [ ] Сделана защищённая резервная копия БД и **проверено восстановление**.
- [ ] Записаны версия кода и хеши SQL; секреты и ключи сохранены отдельно.
- [ ] Сняты суммы `wl_revenue_ledger`, подтверждённых сторно, резервов и выплат;
      список неопределённых платежей, выдач, запусков и уведомлений. Ничего
      автоматически не пересчитывать, даже если старая сумма выглядит неверной.
- [ ] Отдельный миграционный пользователь применяет вручную в изолированной
      базе: `schema.sql` → `commerce.sql` → `enrollment.sql` → `entitlements.sql`
      → `traffic.sql` → `notifications.sql` → `subscriptions.sql` → `finance.sql`
      → `management.sql` → `branding.sql` → `operations.sql` → `public_checkout.sql`
      → `panel_identity.sql`; в Supabase после них **`supabase_security.sql`**
      (и следующие явно указанные миграции
      текущего выпуска). Runtime-пользователь не имеет DDL-прав.
- [ ] `spn_partner_runtime` не владеет таблицами/схемой, не имеет BYPASSRLS,
      административных прав или memberships. Он создан отдельно без пароля
      (`supabase_runtime_role.sql`), LOGIN/пароль активирует сам владелец только
      через защищённый канал. Security migration повторяется после новых таблиц.
- [ ] Перед включением проверены все ограничения/триггеры, повтор SQL и откат
      транзакции. Колонки, найденные `--probe`, не заменяют эту проверку.

## Обязательные внешние проверки до настоящих продаж

- [ ] Нативный PostgreSQL, независимые соединения/процессы: одинаковые и разные
      ключи заказа, два вебхука, две проверки, выплаты одновременно с начислением
      и сторно, advisory lock/FIFO, lease истёкшего воркера. PGlite этого не доказывает.
- [ ] Тестовый мерчант: точная сумма/валюта/metadata/test/shop, потерянный ответ,
      отмена/двойная оплата, восстановление и сутки идемпотентности. Никакой
      партнёр/HTTP-клиент не может сам сообщить `paid=true`.
- [ ] Включено durable invoice intent до внешнего создания счёта:
      `invoice_intents_enabled`. Потерянный ответ не даёт отменить заказ как
      «неоплаченный»; неизвестные intent старше 23 часов идут на сверку, а не
      создают новый платёж. Это отдельный счётчик `invoice_recovery_required`.
- [ ] Настоящая изолированная Remnawave нужной версии: создание/read-back,
      HWID/докупки, срок, NO_RESET, ошибка и потерянный ответ после создания.
- [ ] Граница 30-дневной квоты: ровно 300 ГБ, сохранён остаток докупленных байтов,
      повтор после PATCH/перезапуска, раннее продление, +7 дней без новой квоты,
      ошибка/откат счётчика. Воркер стабильно успевает к границе; опоздание более
      30 минут требует сверки, не выдуманной истории расхода.
- [ ] Реальные Happ/INCY: импорт, обновление, заголовки, имя/бренд, трафик и
      максимум устройств, без подмены HWID и без заявления «VPN подключён».
- [ ] Продление по личной странице: чужой Host/токен, отозванная версия ссылки,
      изменившаяся цена, повтор/новая вкладка/потерянный ответ, открытие старого
      счёта и восстановление после остановки воркера. В URL/HTML/ответах нет
      Telegram ID, исходного URL Remnawave и реквизитов провайдера.
- [ ] Отдельные тестовые боты: getMe → согласие на замену чужого webhook →
      setWebhook → read-back; кнопки/повторы/перезапуск. Ожидание согласия не
      должно попадать в автоматический запуск; pending updates не удаляются.
- [ ] Фактические уведомления по нужному боту, правильный административный
      получатель. `uncertain` не объявляется доставленным и не повторяется слепо.
- [ ] Вывод 1 500 ₽: СБП/USDT, резерв, повтор, нехватка/отрицательный баланс,
      сумма и неизменные реквизиты, ручная выплата с независимым основанием,
      отклонение без потери денег. Автоматические переводы не добавлены.
- [ ] Бренд/сотрудники/маркетинг: чужой tenant, попытки поднять права, вход
      управляющим ботом, отзыв роли, XSS, свежий просмотр рассылки и согласие,
      opt-out/блокировка до отправки. Никаких общих автоматических рекламных
      рассылок от простого включения воркера.
- [ ] DNS/wildcard HTTPS и продление сертификата согласованы отдельно. Не
      перехватываются существующие `@`, `www`, `cdn` и рабочие серверы SPN.
- [ ] У всех прокси/CDN/APM/трассировщиков выключена запись `/s/<секрет>` и

## Старые выдачи и ручная сверка — без бесплатного продления

Если сохранённый конечный срок уже прошёл до успешной выдачи, задача получает
`activation_expired`. Бесконечный повтор не поможет; система не прибавляет
новые 30 дней, не делает второй счёт, не считает платёж потерянным и не снимает
резерв/начисление. Последующие выдачи этой подписки не обходят незавершённую
FIFO-задачу. `--probe` показывает агрегированный счётчик, не публикуя клиентов.
Оператор разбирает подтверждённую оплату, удалённое состояние и фактическую
историю; любое компенсационное решение — отдельная согласованная операция с
основанием и аудитом. Не менять `complete`/срок/баланс произвольным SQL.

Так же отдельно разбираются `legacy_review`, `counter_changed`,
`late_observation`, оплаченные просроченные докупки и неопределённые доставки.
До принятия правил/проверки инструмента такой сверки продажи не открывать.

## Контроль и остановка

Перед открытием небольшому согласованному пилоту проверить бизнес-цикл
целиком; не считать наличие HTTP200 доказательством выдачи/перевода.
Контролировать возраст очереди, не только длину: платежи, активации, запуск,
границу квоты, удержания трафика, lease, `uncertain`, резервы и незакрытые выплаты.
Нужен ответственный оператор и оповещение при остановке/задержке воркера.
Флаги не следует выключать так, чтобы исчезла возможность сверить уже принятые
платежи. Сначала остановить новые продажи/вступления, оставить безопасную сверку.

## Откат

1. Закрыть приём новых заказов, сохранить снимок очередей/балансов и версию кода.
2. Остановить отдельные HTTP/worker-службы; не менять основной `spn-bot`.
3. Не удалять webhook/платёжные события и не повторять отправки/выдачи вручную.
4. Вернуть предыдущую совместимую версию приложения; расширяющую SQL-схему,
   денежные события и действующие ключи не удалять автоматически.
5. Если требуется восстановление БД, сначала вручную сверить все внешние оплаты,
   переводы и выдачи после точки копии. Иначе копия может «забыть» реальные деньги.
6. Проверить суммы/резервы, неопределённые операции и FIFO. Возобновление только
   после отдельного решения владельца; не «лечить» ошибку обнулением данных.
