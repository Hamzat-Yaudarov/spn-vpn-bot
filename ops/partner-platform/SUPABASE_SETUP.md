# Отдельная база всех франшиз

Один отдельный проект Supabase для **всех** партнёров; не проект на каждого
партнёра и не база основного SPN. Общая Remnawave при этом допустима:
принадлежность подписки хранится в партнёрской базе и её неизменной remote identity.
Данные основного бота не копируются и не объединяются автоматически.

Подтверждённый владельцем проект: `SPN franchise`, ref
`crrmaqiakrqpfvhiwtkq`, Tokyo. Это идентификатор, не ключ доступа.
Факт создания не означает, что схема, оплата тарифа, резервное копирование или
внешние интеграции уже проверены. Повторно создавать или менять тариф не нужно.
По отдельному разрешению 21.10.2026 установлены схема и защита; роль остаётся
NOLOGIN, внешние интеграции не включены. Подтверждённое состояние — в
[SUPABASE_INSTALLATION.md](SUPABASE_INSTALLATION.md).

## 1. Подготовка владельцем — до SQL

Проверить выбранный **отдельный** проект и пустую `public`-схему. Затем отключить
Data API либо убрать `public` из exposed schemas; наш кабинет обращается к
своему HTTP backend, не к Supabase REST/GraphQL. Не рассчитывать на одинаковые
автоматические grants у проектов разного возраста. [Защита Data API](https://supabase.com/docs/guides/api/securing-your-api).

Только после отдельного согласования применить SQL в этом проекте. Файлы не
запускаются при старте SPN или runtime. Не выполнять `database.py`/инициализацию
основного SPN. Перед существующими данными нужны отдельная копия и проверенное
восстановление; для новой пустой базы записать этот факт, не изображать backup
данных, которых ещё нет.

## 2. Роль и миграции

`supabase_runtime_role.sql` создаёт `spn_partner_runtime` **NOLOGIN**, без пароля,
без владения схемой и без административных привилегий. Существующая роль не
переименовывается и не получает ослабленные права автоматически.

Отдельный владелец миграций применяет:

`schema.sql` → `commerce.sql` → `enrollment.sql` → `entitlements.sql` →
`traffic.sql` → `notifications.sql` → `subscriptions.sql` → `finance.sql` →
`management.sql` → `branding.sql` → `operations.sql` → `public_checkout.sql` →
`panel_identity.sql` → **`supabase_security.sql` последним**.

Последний файл включает RLS на `wl_*`, отзывает доступ `PUBLIC`, `anon`,
`authenticated`, `service_role` к таблицам, последовательностям и `wl_*`-функциям.
Backend-роли разрешены DML и последовательности, но не DDL/TRUNCATE; для неё
создаётся отдельная server-only RLS policy. Доступ к разным партнёрам по-прежнему
проверяет backend: эта роль доверенная, её пароль никогда не получает браузер.

После **каждой** новой миграции снова применять security-файл: новая таблица без
RLS/server policy блокирует `--probe`. Default privileges не заменяют проверку
всех новых объектов и владельцев. Отдельно проверить отсутствие посторонних
ролей, memberships и оставшихся нестандартных grants. Стандартный `postgres`
не используется приложением; `service_role`/anon API keys тоже не подходят.
У `spn_partner_runtime` запрещено членство в других ролях и получение этой роли
сторонними ролями: иначе они могут унаследовать серверные права и RLS policy,
несмотря на прямые `REVOKE` у API-ролей. Есть только узкое исключение для
PostgreSQL 16+: автоматически созданная связь администратора `postgres` с
`ADMIN=true`, **`INHERIT=false`, `SET=false`**, выданная `postgres` либо
инфраструктурной `supabase_admin`. Она не даёт унаследовать runtime-права или
выполнить `SET ROLE`. Именно такую связь создал этот проект на PostgreSQL 17.11.
Все остальные связи скрипты и `--probe` отклоняют, не удаляя автоматически;
отсутствующие membership options не считаются разрешением.

После проверки владелец самостоятельно задаёт сильный пароль роли через
защищённый административный канал и включает LOGIN. В чат, Git, общую SQL-историю
и frontend пароль не вставлять. До этого роль намеренно не может подключиться;
`--probe` не объявит такую установку готовой. Подключение БД хранится только в
явном owner-only файле конфигурации `0600` на отдельном сервере.

## 3. Соединение: direct или session, не transaction

Выбирать точный адрес через **Connect** выбранного проекта. Direct подходит
постоянному backend; если серверу нужен IPv4, session pooler — подходящая
альтернатива. Transaction mode теряет session-state; наши advisory leases
требуют закреплённой сессии. [Режимы соединения Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres).

Для этого проекта session-адрес без настоящего пароля есть в
`runtime.supabase.example.json`. Это безопасный **выключенный шаблон**, не
готовый запуск. Username соединения — `spn_partner_runtime.<project-ref>`;
Telegram-бот `spn_franchise_bot` — другое назначение и не роль БД.

Явные поля:

- `database_isolation_confirmed: true` — владелец проверил отдельный проект.
- `database_api_disabled_confirmed: true` — отдельно проверено отключение Data
  API/исключение `public`; runtime не выключает его сам и не выдаёт флаг за remote proof.
- `database_project_ref` — сверяется с direct Host или session username.
- `database_connection_mode: direct | session`; порт `6543` запрещён.
- `database_tls: true`; проверяются сертификат и hostname. При необходимости
  `database_ca_file` указывает на явно установленный CA из настроек этого проекта.
- `database_dsn` содержит только партнёрское подключение. Нет fallback к
  `DATABASE_URL`, `.env`, `config.py`, `database.get_pool` основного SPN.

Для session pooler automatic statement cache отключён; это не делает
transaction pooler безопасным для session locks. Пул ограничен 10 соединениями
на процесс: HTTP и worker вместе требуют отдельного расчёта лимита.

## 4. Проверка без запуска продаж

Скопировать шаблон **вне Git**, заполнить локально недостающие настройки стенда
и подтвердить только разрешённые возможности. Домен в примере —
`sub.wayspn.online`; это не меняет DNS, рабочие ссылки основного SPN или TLS.
Новая платформа формирует `https://<партнёр>.sub.wayspn.online/<личный-токен>`;
существующие `/s/...` ссылки поддерживаются для совместимости.

`--check` не подключается к БД. `--probe` внутри read-only транзакции проверяет
схему, сигнатуры таблиц SPN, права backend-роли, RLS и отсутствие API grants.
Он не делает миграций и не публикует hostname, пароль или пользователей.

```sh
python3 scripts/partner_runtime.py --config /etc/spn-partner/staging.json --check
python3 scripts/partner_runtime.py --config /etc/spn-partner/staging.json --probe
```

`database_ready=true` не означает `production_ready=true`: live mode остаётся
запрещённым. Настоящие платежи, внешние Telegram/Remnawave записи, DNS, сертификаты,
перенос на сервер и включение кнопки основного бота согласуются отдельно.

Основной SPN больше не монтирует партнёрские маршруты при рестарте, даже если
в старом окружении остались `PARTNER_*`. Его прежние API/данные не изменяются.
