# TCP TLS + Safari: установка и проверка

Для **новых установок** эта же команда теперь создаёт VLESS TCP **TLS** на 443,
Vision, Safari и настоящий сертификат Let’s Encrypt. SNI совпадает с доменом
сервера. Скрипт создаёт DNS-only A-запись в Cloudflare; свой домен задаётся через
`--domain`, автоматически создаваемый имеет вид `n-a7k2m9.wayspn.com`.

```bash
python3 ~/Downloads/SPNvpnF/ops/universal-reality/deploy.py \
  --ip 217.60.30.79 \
  --domain de11-1-1.wayspn.com \
  --name "🇩🇪 Германия" \
  --country DE \
  --apply
```

Нужны чистая Ubuntu 24.04 и доступный снаружи **TCP80**: Certbot подтверждает
домен через HTTP-01. Скрипт открывает 80/tcp и 443/tcp, а порт управления 2222
разрешает только IP панели. Сертификат и приватный ключ остаются на VPS.
Отдельный фильтр разрешает VPN-порт 443 только на выбранном IPv4; резервные
IPv4 и IPv6 этот порт не обслуживают. Новая TLS-установка отвечает обычным
HTTPS-сайтом без VPN-аутентификации через fallback, поддерживая HTTP/1.1 и HTTP/2.
TLS также отклоняет ClientHello без SNI либо с чужим именем, чтобы не отдавать
сертификат при произвольной проверке IP; это не скрывает трафик от анализа ТСПУ.
`certbot.timer` автоматически продлевает сертификат; после успешного продления
служебный deploy-hook проверяет метку владельца и перезапускает только свою
`remnanode`. Перезапуск кратковременно разрывает подключения. В контейнер
целиком монтируется `/etc/letsencrypt` только для чтения, чтобы работали ссылки
на обновляемые сертификаты. Порт 80 должен оставаться доступным для продления.

После успешной проверки VPN установка автоматически регистрируется в панели
резервных IP. По умолчанию локальный реестр: `~/.spn-reserve-fleet`; для другого
каталога используй `--fleet-dir`. Если регистрация прервана, повтор той же команды
завершает её с сохранением существующих объектов.

Для смены адреса уже созданного сервера есть
[`change_ip.py`](change_ip.py) и [инструкция](REPLACE.md).

**Старые сохранённые REALITY-установки сохраняют прежний транспорт.** Они не
переделываются в TLS при повторном запуске. Для нового REALITY вместо TLS явно
добавь `--transport reality`. VK-реле продолжают использовать
[свой установщик](../universal-vk/README.md). Только у REALITY остаются HAProxy
на публичном 443, закрытый инбаунд `127.0.0.1:2443`, PROXYv2 и прежний SNI
`www.cloudflare.com`; у TLS Xray принимает соединения на 443 самостоятельно.

Схема сертификатов и Vision сверена с
[официальной конфигурацией Xray](https://github.com/XTLS/Xray-examples/blob/main/VLESS-TCP-XTLS-Vision/config_server.jsonc),
а выпуск и продление — с
[документацией Certbot](https://eff-certbot.readthedocs.io/en/stable/using.html).

Если Ubuntu занята автоматическим обновлением пакетов, установка ждёт
освобождения APT/dpkg до 10 минут. Lock-файлы не удаляются, процессы обновления
не прерываются.

Зависимости, включая HAProxy или Nginx, устанавливаются до сохранения и
применения исходящего маршрута. Пакетные обработчики Ubuntu могут перезапустить
networkd и пересоздать маршрут; после установки пакетов скрипт проверяет уже
актуальное состояние. Повторный запуск использует отметки готовых пакетов.

## Один раз: доступ к Cloudflare

В Cloudflare создай API Token: **Zone → DNS → Edit** и **Zone → Zone → Read**,
Zone Resources — только конкретная зона `wayspn.com`. Глобальный API Key и
пароль аккаунта не нужны. Токен не присылай в чат.

Сохрани его на Mac скрытым вводом:

```bash
python3 ~/Downloads/SPNvpnF/ops/universal-reality/setup_cloudflare.py
```

Файл `~/.config/spn/cloudflare-token` создаётся с правами 0600 в папке 0700;
существующий файл не перезаписывается. Токен не передаётся на VPS или в панель,
не записывается в план установки и не печатается. Вместо файла можно использовать
`CLOUDFLARE_API_TOKEN` в окружении или локальном `.env`. Для другого приватного
файла укажи одинаковый путь в `setup_cloudflare.py --file /путь/к/токену` и
`deploy.py --cloudflare-token-file /путь/к/токену`.

## Одна команда на Mac

Нужна чистая Ubuntu 24.04, root-доступ и публичный IPv4, уже назначенный VPS.
Команду запускай на Mac, а не внутри SSH:

```bash
python3 ~/Downloads/SPNvpnF/ops/universal-reality/deploy.py \
  --ip НОВЫЙ_IP \
  --name "🇫🇮 Финляндия" \
  --country FI \
  --apply
```

Замени IP, название и страну. Сквады выбираются при запуске. Можно передать
`--squad regular`; для нескольких сквадов повторить флаг. API-токен читается из
`.env`, иначе запрашивается скрытым вводом; на VPS токен панели не передаётся.
Пароль VPS вводится в обычном запросе SSH и скриптом не сохраняется.

Домен создаётся автоматически в `wayspn.com`. Своё имя можно указать через
`--domain fi105.wayspn.com`; другую Cloudflare-зону — через `--dns-zone example.com`
с доступом токена именно к ней. Используется одна A-запись, **DNS only / серое
облако**, TTL 60; AAAA не создаётся. Для TLS SNI и имя сертификата совпадают
с доменом подключения. Только у прежнего REALITY SNI остаётся `www.cloudflare.com`.

Чужие DNS-записи не перезаписываются. При потере ответа на создание скрипт
сначала ищет запись по своей служебной метке, а не создаёт дубликаты. Нужен `dig`
и доступ к публичным/авторитетным DNS: до публикации ноды проверяются реальная
делегация, точная A-запись и отсутствие AAAA, без системного FakeIP-резолвера.
Если запись ещё не распространилась, повтори ту же команду — домен сохраняется.

Эта возможность действует только для **новых прямых установок**. Старые планы
с IP не мигрируются автоматически и не требуют токена Cloudflare; обходы VK
и выданный им внешний адрес/порт не меняются.

Профиль, инбаунд, нода и хост получают одинаковый случайный код из 6 букв и цифр:
`TLS_a7k2m9`, `tls-a7k2m9`, `🇫🇮 Финляндия • TCP a7k2m9`.
Код проверяется на занятость. Повтор прежней команды сохраняет код, ключи и UUID,
а не создаёт дубликаты. Без `--apply` — только локальный план, без сети и изменений.

## Резервные IP

Можно держать три IP на VPS: один действующий и два резервных. **В DNS должна
быть только одна A-запись с действующим IP**, не три адреса одновременно.
Резервный IP сначала нужно назначить VPS и проверить из нужной российской сети;
то, что он отвечает по SSH, ещё не доказывает доступность VPN-порта.

При замене IP сохраняются домен, профиль, ключи и хост. Но одной правки DNS
недостаточно: нужно выбрать новый исходящий IPv4 и обновить его сохранение на
VPS, затем заменить содержимое A-записи в Cloudflare и проверить соединение.
Удаляй старый IP только после успешного переключения. Переподключение клиентов
и сброс их DNS-кэша могут занять больше 60 секунд. При обычном повторе старой
команды скрипт не возвращает DNS обратно на старый IP: он остановится на
изменившейся записи, чтобы не отменить ручное переключение.

Этот установщик **не покупает IP**, не выбирает и не удаляет резервные адреса.
Постоянная работоспособность трёх адресов не гарантирована: блокировка может
затронуть весь их диапазон.

Новые установки включают `node_guard.py`: собственную таблицу nftables до
перенаправлений Docker, сохранение правил после загрузки и ежедневное обновление
проверяемого списка известных сканеров. Входящий TCP443 разрешён только текущему
IPv4, на резервах и IPv6 закрыт. Проверки SSH на резервных IPv4 продолжают работать:
сам порт 22 не ограничивается адресом контроллера, но подключения из списка
сканеров отбрасываются. Московский контроллер `147.45.164.28` и IP панели исключены
из этого списка; исключения не обходят запрет VPN на резервах.

Используется только общественный
[antiscanner.list](https://github.com/shadow-netlab/traffic-guard-lists/blob/main/public/antiscanner.list),
без широкого списка государственных сетей. Проверяются HTTPS-источник, формат,
размер и диапазоны. Недоступное или некорректное обновление не заменяет последнюю
рабочую политику. Это дополнительная фильтрация известных источников, а не
подтверждение, что все такие подключения принадлежат РКН или что все сканеры учтены.

REALITY получает дополнительный SNI-фильтр HAProxy: до Xray проходят только
ClientHello с настроенным именем целевого сайта. Его обновление хранится отдельно
от исходной конфигурации и не меняет ключи, UUID, профиль и транспорт.

Для уже зарегистрированной установки используйте `harden` на контроллере:

```sh
cd /opt/spn-reserve-fleet/current
runuser -u spn-reserve -- \
  /opt/spn-reserve-fleet/venv/bin/python -m spn_reserve_fleet \
  --data-dir /var/lib/spn-reserve-fleet/.spn-reserve-fleet \
  --env-file /var/lib/spn-reserve-fleet/config/remnawave.env \
  harden --server ДОМЕН_СЕРВЕРА --apply
```

Без `--apply` команда показывает план. Она добавляет сетевой фильтр и SNI-проверку
для REALITY либо сайт для старого TLS, сохраняя исходный транспорт и план. Перед
защитой необходимо завершить незавершённую смену IP; после обрыва повторяют тот же
`harden`. Доступ для управления возможен через резервный SSH, активный VPN-IP от
этого не меняется. Подробности — в [панели резервов](../../spn_reserve_fleet/README.md).

`change_ip.py` переносит разрешение VPN-порта атомарно после проверки прежней VPS
и до обновления DNS. Ошибка применения или проверки фильтра останавливает смену
и не позволяет записать успешное завершение. Возобновлять нужно ту же операцию
на тот же IP. Защита от сканирования и обычный сайт не гарантируют обход ТСПУ,
пассивного распознавания VPN-трафика или блокировки всего диапазона адресов.

Не запускай установщик с другим `--ip` для обычного переключения на резерв:
новый `--ip` означает отдельную установку с новым кодом и доменом, а не смену
адреса существующего хоста. Для замены целиком новой VPS используй `replace.py`;
это не переключатель дополнительных IP на той же работающей VPS.

Полная замена TLS- или REALITY-VPS сохраняет домен, клиентские UUID, профиль,
инбаунд, хост и выбранные сквады. Укажи исходный каталог установки:

```bash
python3 ~/Downloads/SPNvpnF/ops/universal-reality/replace.py \
  --domain ИСХОДНЫЙ_ДОМЕН --ip НОВЫЙ_IP \
  --state-dir КАТАЛОГ_ИСХОДНОЙ_УСТАНОВКИ --apply
```

На новой чистой Ubuntu 24.04 должен работать прежний SSH-порт. Перенос
SSH-порта во время полной замены пока запрещён. Скрипт не меняет тип транспорта:
TLS остаётся TLS, REALITY сохраняет свои ключи. Для запуска с контроллера нужны
`--non-interactive`, настроенный API-токен и закреплённое SSH-доверие; проверка
`--test-route system` подтверждает работу VPN через сеть самого контроллера.

Для TLS на компьютере или контроллере, запускающем замену, нужны `certbot`,
`openssl` и `dig`. До установки новой VPS выпускается свежий сертификат через
DNS-01: временный TXT создаётся отдельно от действующей A-записи, а затем
удаляется по собственному маркеру и ID. Cloudflare-токен остаётся на контроллере.
Доступ к старой VPS не требуется. На новую VPS по доверенному SSH передаются
сертификат, его приватный ключ и отдельная ACME-учётная запись этой операции;
дальнейшее продление выполняет обычный `certbot.timer` через HTTP-01/TCP80.

DNS переключается после установки, проверки защиты и VPN-теста 9/9. После
ошибки повтори ту же команду с тем же IP: незавершённая операция не заменяется
другой. Старую VPS скрипт не удаляет, автоматического отката после переключения
DNS нет. Удалять старую VPS следует после успешной проверки подключения клиента.

## После ошибки, очистки VPS или покупки нового IP

Повтори ту же команду. Для уже известного IP можно короче:

```bash
python3 ~/Downloads/SPNvpnF/ops/universal-reality/deploy.py --ip ТОТ_ЖЕ_IP --apply
```

Скрипт проверяет саму VPS даже после прежнего завершения: если ОС была
переустановлена, заново ставит ноду, используя сохранённые записи панели.
`--reinstall` оставлен для совместимости; он допустим и с новым IP, но теперь
не обязателен. Сам скрипт ОС не переустанавливает и чужие службы не удаляет.

Дополнительный IP не обязан сразу быть исходящим по умолчанию. Скрипт проверит
его исходящий HTTPS, сохранит прежний простой маршрут и выберет нужный IPv4,
не меняя шлюз/интерфейс и не перезапуская сеть. При ошибке изменения откатываются.
Выбор сохраняется собственным systemd oneshot для запуска после загрузки.
Netplan, ifupdown и cloud-init не переписываются. Нестандартная policy routing
и несколько default routes намеренно не переделываются автоматически.

Если старый запуск остановился с `Default route changed outside this operation`,
сначала сравнивают фактический маршрут с сохранённым планом. Для подтверждённого
перехода `boot` → `static` есть отдельный `source_recovery.py`: он требует
проверенные machine-id и SHA256 точного маршрута, сохраняет исходный план и
возобновляет частично завершённое восстановление. Без `--apply` выполняется
только проверка. Он не принимает изменения шлюза, интерфейса, метрики или
постороннего исходящего IP и не меняет код прежнего загрузочного помощника.

Код страны ноды в панели можно исправить вручную (например, `AU` — Австралия,
`AT` — Австрия). Продолжение установки сохраняет эту метку у ноды с известным
UUID; адрес, порт, профиль и инбаунды по-прежнему должны совпадать с журналом.

Если на той же VPS остался старый назначенный IP и собственная старая нода
панели, скрипт выключит её и собственный старый хост, не удаляя их. Это не даёт
двум контроллерам одновременно подменять конфигурацию одного ядра. Владение
подтверждается локальными UUID-квитанциями и адресами самой VPS; чужую ноду
скрипт автоматически не выключает, чужие и общие профили не меняет.

## SSH после переустановки

Общий `~/.ssh/known_hosts` не очищается. Скрипт ведёт отдельное приватное доверие,
переиспользует уже подтверждённый неизменный ключ и не спрашивает его каждый раз.
Если ключ изменился, скрипт останавливается для явного подтверждения. Более
безопасный вариант — сверить отпечаток в веб-консоли VPS у хостинга:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
```

Вставь полный `SHA256:...` из результата. Если ты **сам переустановил эту VPS**
и проверил её IP у хостинга, вместо VNC можно явно ввести в скрипте
`ПЕРЕУСТАНОВЛЕН НОВЫЙ_IP` (с настоящим IP). Это осознанное принятие нового ключа
без независимой проверки, поэтому риск подмены не исключается. Выбор фиксируется
в приватном журнале; прежние ключи и общий `known_hosts` не удаляются.
Просто `yes` для изменённого ключа не принимается.
Можно передать заранее сверенный отпечаток через
`--host-key-sha256 'SHA256:...'`; после подтверждения он сохраняется для повторов.
Для первого неизвестного IP возможно обычное явное первое доверие SSH.

## Что теперь означает «готово»

Одних открытых портов недостаточно. До сообщения «Готово» выполняются:

1. Проверка назначения IPv4, исходящего HTTPS, маршрута и его сохранения.
2. Проверка связи с панелью, привязок профиля, Docker, слушателей и firewall.
3. Девять реальных запросов через изолированный VLESS TLS/Safari-клиент (REALITY у прежних установок): HTTPS,
   совпадение выходного IP, загрузка 1 МБ и параллельные запросы.
4. Проверка фактической выгрузки подписки: адрес, порт, Safari, SNI, а для REALITY — открытый
   ключ, short ID и Vision. При ошибке новый только что включённый хост выключается.

Проверочный клиент не имеет DIRECT fallback. По умолчанию `--test-route auto`:
сначала прямой тест через физический `en0`, а если ограничения мешают — отдельная
проверка самой настройки через временный локальный SSH-канал до этой же VPS.
Для другого физического интерфейса укажи `--interface en5`.
Системный VPN не переключается.

**Если сейчас включены белые списки**, можно сразу указать `--test-route ssh`.
Так можно проверить саму настройку нового сервера через административное соединение,
но это **не доказывает** его прямую доступность и обход ограничений. Результат
так и помечается: «проверено через SSH; прямой доступ не подтверждён».
Клиент всё равно проходит настоящую VLESS/TLS-аутентификацию (REALITY у прежних установок), а данные выходят
в интернет с нового IP; просто входящее соединение доставляется через SSH.
Для строгого прямого теста есть `--test-route physical`. Для теста через текущие
системные маршруты Mac (например, действующий TUN-VPN) есть `--test-route system`.

Для теста используется **существующая** подписка из приватного файла
`~/Downloads/SPNvpnF/.vpn-test-link.txt` с правами 0600. В этом проекте она уже
предоставлена для проверки. Можно указать другой файл через
`--test-subscription /полный/путь/к/файлу`. Нужен активный пользователь с доступом
к выбранным сквадам. Новые пользователи, покупки и балансы не создаются.
Ссылка и пользовательские UUID не печатаются и не передаются в argv.

Проверка рассчитана на Mac Apple Silicon. Официальный Xray 26.9.9 сохраняется
в приватный кэш; при отсутствии скачивается из закреплённого GitHub-релиза.
До запуска обязательно проверяется фиксированный SHA256 бинарника.
Можно передать тот же проверенный бинарник через `--engine /путь/к/xray`.

Если ни один выбранный режим VPN-теста не проходит, скрипт не выдаёт установку
за рабочую и не включает новый хост. Прогресс и обезличенный результат сохраняются.
Успешный тест не гарантирует доступность IP у всех операторов навсегда и не
обещает обход белых списков прямым подключением.

## Что сохранять

Не удаляй `~/.spn-reality-deploy/`: там ключи, UUID, SSH-доверие, кэш и прогресс.
Сделай защищённую копию; не публикуй и не добавляй в Git. Сохраняй всю папку
проекта: используются общие функции `ops/universal-direct` и `ops/host-health-audit`.
Для перенесённого состояния есть `--state-dir`.

## Если IP уже указан у старой ноды панели

Это не конфликт отображаемого названия: адреса нод в панели уникальны, даже у
выключенных записей. Скрипт показывает название и UUID существующей записи.
Он не считает её своей только по совпадению IP.

Если VPS очищена и эта прежняя запись больше не нужна, при обычном интерактивном
запуске подтверди замену словом `ЗАМЕНИТЬ`. Можно явно выбрать ту же запись:

```bash
python3 ~/Downloads/SPNvpnF/ops/universal-reality/deploy.py \
  --ip НОВЫЙ_IP --name "Германия" --apply --test-route ssh \
  --replace-node UUID_ПРЕЖНЕЙ_НОДЫ
```

Замена сохраняет UUID ноды, но задаёт ей новое имя со случайным кодом и новый
профиль TCP TLS (либо REALITY при явном выборе). Прежние профили и сквады не удаляются и не переделываются.
Выключаются только старые хосты, однозначно привязанные исключительно к этой
ноде и её прежним инбаундам; общие хосты не меняются. Сначала проходит SSH-проверка
чистой/собственной VPS, и только после неё меняется панель. Подтверждение и снимок
сохраняются локально; после обрыва используется та же операция без дубликатов.
Если параметры записи кто-то изменил во время замены, скрипт останавливается.

Вручную удалять ноду или указывать ей выдуманный IP для освобождения адреса
не нужно. Если установленная VPS не очищена и принадлежит другому установщику,
`--replace-node` не разрешает сносить её файлы и службы.

Локальные тесты без реальной сети и VPS:

```bash
cd ~/Downloads/SPNvpnF
python3 -m unittest discover -s ops/universal-reality -p 'test_*.py'
```
