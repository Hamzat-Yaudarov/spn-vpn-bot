# Внешняя проверка через выбранные EU VPS

Локальная реализация: `spn_ip_failover.dynamic_relay_worker`. Ничего не
установлено или включено этой доработкой. Она не читает billing credentials
и не вызывает заказ, удаление IP или изменение панели.

Внешний воркер исполняется на российском контроллере. Он читает **только**
текущий IPv4 разрешённой ноды через Remnawave и поднимает короткий SSH SOCKS
туннель к ограниченному непривилегированному пользователю EU VPS. Xray и
клиентские ключи остаются на российском контроллере. У relay не появляется
доступ к токену панели или учётным данным хостинга.

Один из двух разных EU VPS выбирается так, чтобы он не совпадал ни с нодой,
ни с услугой, ни с адресом VPN-кандидата. На выбранном relay сначала нужен
успешный контрольный HTTPS-запрос. При сбое SSH/контроля можно проверить
второй relay. Подтверждённый VPN-отказ не запускает перебор всех relay.
Смена IP relay во время проверки аннулирует результат. При ошибках выходит
только `{"status":"unknown"}` без чувствительной диагностики.

Воркера ограничивает POSIX-таймер 35 секунд: остаётся время для штатной
очистки Xray/curl/SSH до внешнего таймаута контроллера 55 секунд. Не более
двух попыток relay за запрос.

Приватная конфигурация `0600` в каталоге владельца `0700`:

```json
{
  "version": 1,
  "remnawave": {
    "url": "https://panel.example.invalid",
    "credential": "remnawave"
  },
  "routes": {
    "UUID_ХОСТА": {
      "node_uuid": "UUID_ЕГО_НОДЫ",
      "service_id": "UUID_ЕГО_УСЛУГИ_1CENT"
    }
  },
  "relays": [
    {
      "node_uuid": "UUID_НОДЫ_RELAY_1",
      "service_id": "UUID_УСЛУГИ_RELAY_1",
      "user": "spnrelay",
      "identity": "/var/lib/spn-ip-failover/.ssh/relay_ed25519",
      "known_hosts": "/var/lib/spn-ip-failover/.ssh/relay_known_hosts",
      "ssh_port": 22
    },
    {
      "node_uuid": "UUID_НОДЫ_RELAY_2",
      "service_id": "UUID_УСЛУГИ_RELAY_2",
      "user": "spnrelay",
      "identity": "/var/lib/spn-ip-failover/.ssh/relay_ed25519",
      "known_hosts": "/var/lib/spn-ip-failover/.ssh/relay_known_hosts",
      "ssh_port": 22
    }
  ]
}
```

UUID должны быть настоящими каноническими UUID; выше только шаблон.
Доверенный SSH-ключ каждого relay записывается под неизменным alias
`spn-ip-rotation-relay-<UUID_УСЛУГИ>`. Нельзя генерировать доверие из
`ssh-keyscan` или автоматически заменять ключ при смене IP. Изменяется
лишь TCP-адрес подключения; `StrictHostKeyChecking=yes` сохраняется.

Токен берётся не из argv или произвольной переменной окружения, а только
из systemd credential с фиксированным именем `remnawave` внутри
`/run/credentials/<имя-службы>/`. Путь должен быть абсолютным, без symlink;
файл — владельца службы или root, режим `0400`/`0600`. `Probe.run` передаёт
дочернему процессу только путь `CREDENTIALS_DIRECTORY`, не значения токенов
или паролей.

Команда probe в будущем закрытом конфиге контроллера:

```sh
/usr/bin/python3 -B -m spn_ip_failover.dynamic_relay_worker \
  --config /var/lib/spn-ip-failover/routes.json \
  --relay-config /var/lib/spn-ip-failover/outside-relays.json
```

Перед включением нужны:

1. Минимум два выбранных EU VPS с подтверждённой физической независимостью
   от проверяемого backend и рабочим исходящим интернетом.
2. Проверенные SSH host keys; отдельный ключ контроллера и ограниченный
   non-root SSH пользователь. Только нужное TCP forwarding, без shell,
   PTY, agent forwarding, произвольных команд или изменения файлов.
3. Ограничение доступных портов на relay. Ограничение порта само по себе
   не гарантирует публичность адреса; это учитывать при настройке sshd/
   firewall, не объявлять полноценной сетевой изоляцией.
4. Переданный в службу credential `remnawave`, приватные файлы конфигурации,
   подтверждённый реальный end-to-end тест и очистка временного SSH процесса.

Если оба EU relay недоступны из РФ, результат остаётся `unknown`.
Нельзя покупать IP, опираясь на неисправную внешнюю точку проверки.
