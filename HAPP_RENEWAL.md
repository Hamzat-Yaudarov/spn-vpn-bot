# Бесплатный переход из Happ / INCY → продление на сайте

Включено на рабочем сервере и в Remnawave 6 октября 2026 года.
Страница `https://wayspn.ru/renew`, её API и индивидуальные заголовки работают.
Отчёт об установке: `ops/subscription-renewal/DEPLOYED.md`.

## Как работает

1. Happ / INCY получает индивидуальную ссылку `https://wayspn.ru/renew#{{SUBSCRIPTION_URL}}`.
   Remnawave подставляет URL именно той подписки, в которой отображается ссылка.
   В Happ пользователь нажимает ⓘ слева от трафика, в INCY — кнопку «🌐 Сайт».
   Текст над серверами объясняет, куда нажать, и сохраняет предупреждение про «ОБХОД».
2. Сайт открывает её тип, номер и срок действия. Вход в Telegram/кабинет не нужен.
3. Пользователь выбирает 30/90 дней и оплачивает через YooKassa.
   Тарифы и действующие скидки берутся из того же расчёта, что и в боте;
   отдельных цен продления на сайте нет.
4. Продлевается та же подписка. Старая ссылка и настройки подключения не меняются.

Ссылка не открывает полный кабинет: нельзя получить другие подписки, VPN-ключи,
удалить подписку, менять устройства или тратить реферальный баланс.
Сама ссылка — секрет: её нельзя публиковать или отправлять посторонним.
В этой реализации она использует существующий секрет ссылки подписки, а не
отдельный платёжный пароль. Перевыпуск URL подписки отзывает старую ссылку продления.

## Что требуется для включения

- Рабочая версия этих файлов на VPS бота, где работают сайт и платёжный API.
  Миграции схемы БД не нужны, `.env` не меняется.
- `PUBLIC_SITE_URL` — HTTPS-сайт (по текущему умолчанию `https://wayspn.ru`).
- `SUBSCRIPTION_PUBLIC_BASE_URL` — тот же HTTPS-хост, который Remnawave подставляет
  в `{{SUBSCRIPTION_URL}}` (по текущему умолчанию `https://sub.wayspn.online`).
  Допустимые пути: `/<shortUuid>` или `/sub/<shortUuid>`. Чужие хосты/HTTP отклоняются.
- Proxy сайта должен передавать `/renew` и `/site/api/renewal/` в приложение бота,
  а `/site/assets/renew.css` и `/site/assets/renew.js` — отдавать без подмены HTML.
  Нельзя писать `Authorization` в логи и нельзя кешировать страницу/API.
- Remnawave 3.x с Additional Response Headers и переменной `{{SUBSCRIPTION_URL}}`.
  Не обновлять панель только ради этих изменений без отдельного бекапа/проверки.
- Provider ID и Premium **не нужны для выбранного бесплатного варианта**.
  Ранее полученный Happ Provider ID не используется в новых заголовках.
  Платные `sub-info-*`, `sub-expire-*`, `banner-*` и `premium-url` не генерируются.
  Никакие тарифы приложений здесь не подключаются и не оплачиваются.

Используется стандартная кнопка/иконка сайта через `profile-web-page-url`:
она открывает страницу продления. Произвольная подпись «Продлить» для этой кнопки
не предусмотрена: в присланной версии INCY она называется «Сайт», в Happ это ⓘ.
Заметная инструкция добавляется бесплатным параметром `announce`, не баннером Premium.

## Заголовки Remnawave

Сначала установить/проверить страницу, и только потом включать заголовки.
Сгенерировать их без обращений к живой панели:

```sh
python3 scripts/prepare_happ_renewal.py --site-url https://wayspn.ru --client both
```

В Remnawave: Subscription → Settings → Additional Response Headers.
**Добавьте или обновите только выведенные поля**, сохранив остальные заголовки,
маршрутизацию, лимиты и конфигурации серверов. Текущий `announce` заменяется коротким
текстом с инструкцией продления **и** предупреждением про «ОБХОД», не удаляя смысл
предупреждения. Если есть другие важные объявления, сначала объедините их с новым
текстом и проверьте лимит 200 символов. Не подставляйте одну тестовую ссылку для всех!

- `profile-web-page-url`: `https://wayspn.ru/renew#{{SUBSCRIPTION_URL}}`.
  Это намеренно заменяет переход на прежнюю страницу подписки переходом на продление.
- `announce`: короткая инструкция в формате `rwEncodeBase64:...`.
- `announce-url` не добавляется: INCY показывает его отдельной кнопкой «Канал/Бот»,
  которая дублировала продление. Этот заголовок удалён из рабочей настройки
  6 октября 2026 года после проверки пользователем. Переход остаётся через «Сайт».

Готовые заголовки: `ops/subscription-renewal/response-headers.json` — **рекомендуемый
общий набор для обеих программ**, без необходимости настраивать определение клиента.
Текст в обоих приложениях будет одинаковым:

> 💳 Продление: Happ — ⓘ слева от трафика; INCY — «🌐 Сайт».
>
> Подключайтесь к «ОБХОД» только во время ограничений интернета.

Также подготовлены `response-headers-happ.json` и `response-headers-incy.json` с
подсказкой только для соответствующего приложения. Их можно использовать в
отдельных клиентских правилах, **если они уже настроены**. Не добавляйте оба набора
в глобальные заголовки одновременно: один `announce` перезапишет другой.
Генератор выбирает вариант через `--client happ|incy|both`.

`support-url` не выводится по умолчанию: текущая «Поддержка» остаётся без изменений,
даже если локальный `.env` отличается от рабочей панели. Явная замена возможна
только при передаче `--support-url https://...`. Это **не полный объект subscription
settings**, не заменять файлом все настройки панели. Если ранние платные заголовки
из этой задачи уже внесены вручную, сначала сохраните их копию и уберите только их,
не затрагивая существующие настройки провайдера, сделанные вне этой задачи.

`rwEncodeBase64:` — префикс **настройки Remnawave**, не итогового HTTP-ответа.
В ответе панель должна отдать `base64:...`, а ссылка должна содержать реальный URL
конкретной подписки, не фигурные скобки. В итоговом HTTP-ответе не должно быть сырого
переноса строки из настройки: он находится внутри текста, закодированного в Base64.
На рабочем сервере проверены заголовки для запросов Happ / INCY: переменная
раскрывается в реальную ссылку именно этой подписки, объявление приходит в Base64,
поддержка сохранена. Точное отображение подсказки и переход по фрагменту в реальных
версиях приложений остаются для ручной проверки: сами Happ / INCY не запускались.

## Проверка без списания денег

1. Обновить одну тестовую подписку в Happ и INCY; проверить текст, переход через
   ⓘ / «Сайт» и сохранение кнопки поддержки. В INCY не должно быть второй кнопки
   «Канал/Бот», открывающей ту же страницу продления.
2. Убедиться, что сайт показывает правильный тип/номер/срок, даже если у пользователя
   несколько подписок. Проверить обычную, bypass и истёкшую подписки.
3. Выбрать срок. Цена должна совпадать с ботом с учётом текущих общих скидок.
4. Открыть счёт YooKassa **без оплаты**, вернуться/обновить страницу. Один повтор
   запроса с тем же request ID не должен создавать второй счёт.
5. Для проверки реального продления нужна отдельно разрешённая тестовая оплата.
   Локальные тесты используют моки и не доказывают работу живой цепочки оплаты.

## Защита платежей и ссылки

- Секрет приходит во фрагменте `#`, поэтому не попадает в URL HTTP-запроса/обычные
  access-логи **сайта продления**. JS сразу убирает фрагмент из адресной строки и истории
  текущей вкладки. Административный endpoint Remnawave `users/by-short-uuid` содержит
  shortUuid в пути: его логи также нужно защищать/редактировать, как логи подписок.
- Для возвращения из оплаты он хранится только в `sessionStorage` этой вкладки.
  Не используется `localStorage`. При закрытии вкладки её сессия обычно исчезает;
  пользователь может снова нажать ⓘ в Happ / «Сайт» в INCY. Возврат после оплаты не требует
  передачи секрета YooKassa — `return_url` содержит только `?payment=return`.
- Сайт не загружает сторонние скрипты/аналитику. CSP ограничивает скрипты, запросы
  и стили своим доменом; `Referrer-Policy: no-referrer`, `no-store`, запрет iframe.
- Сервер проверяет shortUuid через закреплённый административный API Remnawave
  с проверкой TLS. По публичной ссылке он ничего не скачивает: нет SSRF на чужие URL.
  При недоступности панели проверка закрывается, не выдаёт доступ по старому кешу.
- Скрытые/непродлеваемые/старые readonly-записи не открываются. Истёкшая, но доступная
  к продлению v2-подписка разрешена.
- Тип, владелец, ID подписки и цена берутся сервером, не из запроса браузера.
  При изменении цены перед созданием счёта требуется обновить страницу.
- Повторный checkout использует один ключ идемпотентности YooKassa. Повторная запись
  счёта в БД не сбрасывает статус `paid`. Неудачный checkout не заменяет старые счета.
- Проверка успешной оплаты использует общий `reconcile_payment` и механизм
  идемпотентной активации бота. Вебхук, фоновая проверка и ручная проверка не добавляют
  срок повторно **за один invoice**. Два разных оплаченных счёта — две покупки.
- Если пользователь закрыл оплату/страницу, запись остаётся в общей очереди бота.
  Следующее открытие может подхватить ожидающий счёт этой подписки; проверка оплаты
  в фоне не зависит от страницы или `return_url`.
- Ограничения запросов в процессе приложения — дополнительная защита. На proxy
  нужен обычный лимит запросов по IP; IP должен передаваться доверенным proxy,
  не произвольным `X-Forwarded-For` от клиента.

```sh
python3 -m unittest discover -s tests -p 'test_subscription_renewal.py'
python3 -m unittest discover -s tests -p 'test_payment_reconciliation.py'
python3 -m unittest discover -s tests -p 'test_payment_recovery.py'
```

Первоначально выполнены 30 новых API/безопасность/метаданные/идемпотентность-тестов,
5 тестов reconciliation, 23 payment recovery, 23 UI, 34 Remnawave v3 и 19 mobile security.
Добавлены регрессии бесплатных заголовков: подписи реальных элементов Happ/INCY,
сохранение предупреждения «ОБХОД», лимит 200 символов, отсутствие платных полей,
синхронность JSON-файлов и генератора, сохранение поддержки. Добавлена отдельная
проверка совпадения всех цен сайта с расчётом бота при общих и адресных скидках.
После выбора бесплатного варианта повторно прошли 35 тестов продления, 5 тестов
reconciliation, 23 теста payment recovery и все 6 браузерных сценариев.
